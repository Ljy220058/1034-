# 活动复盘摘要自动生成方案

## 1. 方案目标

在活动结束后，为管理员提供一份可直接阅读的中文“活动复盘摘要”。摘要内容不依赖人工整理，优先复用现有数据库数据，做到“最小改造、一次生成、可追溯”。

本方案只做调研与文档设计，不修改业务代码。设计原则如下：

1. 复用现有活动、报名、签到、成员、工作区待办等数据源。
2. 只提供只读聚合接口，不引入新的写操作。
3. 输出结构固定，便于前端页面和后续管理后台复用。
4. 结果全部中文，避免与现有提醒、候补、补签、撤销等模块语义重复。

## 2. 现有可复用数据源

结合仓库现状，已经存在的可复用数据来源主要有：

1. `backend/routes/activities.py`
   - 活动基本信息、活动列表、活动详情。
   - 可提供活动名称、时间、距离、地点、状态等基础字段。

2. `backend/routes/activities.py` 中的报名接口
   - 报名记录可直接反映报名人数。
   - 可用于统计报名人数、报名成员名单、报名与签到差值。

3. `backend/routes/checkins.py`
   - 活动签到记录、补签记录、撤销记录。
   - 可用于统计签到人数、签到时间分布、异常签到和已撤销签到。

4. `backend/routes/members.py`
   - 成员基础信息和角色信息。
   - 可用于将报名/签到记录映射到成员姓名，生成缺席统计。

5. `backend/routes/workspaces.py` 与任务相关模块
   - 可作为“后续待办”的来源，尤其适合生成活动后需要补处理的事项。

6. `backend/app.py` 的统一错误处理与 API 返回格式
   - 已经固定了 `{"data": ..., "message": "成功"}` 和 `{"detail": "..."}` 的结构。
   - 复盘摘要接口应沿用这一规范。

## 3. 最小可落地的数据口径

为了保证 30 分钟内可落地，建议复盘摘要只统计以下 5 类信息：

1. 报名人数
   - 口径：活动报名记录总数。
   - 用途：判断活动预热效果。

2. 签到人数
   - 口径：有效签到记录数，排除撤销签到。
   - 用途：判断实际到场情况。

3. 缺席成员统计
   - 口径：已报名但未签到的成员列表及人数。
   - 用途：快速定位未到场成员，便于后续跟进。

4. 反馈摘要
   - 口径：活动结束后管理员填写的总结文本，或活动结束后系统自动拼接的简短归纳。
   - 用途：沉淀活动经验。

5. 后续待办
   - 口径：活动结束后需要处理的事项，例如补录签到、催补反馈、整理照片、更新成员状态等。
   - 用途：形成闭环。

## 4. 接口设计

### 4.1 后端接口

建议新增一个只读接口：

- 路径：`GET /api/v1/activities/{activity_id}/recap-summary`
- 返回：`ApiResponse`
- 权限：管理员、团长可读

返回建议结构如下：

```json
{
  "data": {
    "activity": {
      "id": 1,
      "title": "周末晨跑",
      "starts_at": "2026-06-01T07:00:00+08:00",
      "distance_km": 8.0
    },
    "summary": {
      "registered_count": 24,
      "checked_in_count": 19,
      "absent_count": 5,
      "absent_members": [
        {"member_id": 3, "name": "张三"},
        {"member_id": 7, "name": "李四"}
      ],
      "feedback_brief": "天气适合跑步，整体出勤率较高。",
      "follow_up_items": [
        "补录未提交的签到说明",
        "整理活动照片并归档",
        "跟进未到场成员的原因"
      ]
    }
  },
  "message": "成功"
}
```

### 4.2 前端入口

建议前端在活动详情页增加一个“生成复盘摘要”按钮或卡片入口：

1. 管理员进入活动详情页。
2. 活动状态为“已结束”时，按钮高亮可用。
3. 点击后请求 `/api/v1/activities/{activity_id}/recap-summary`。
4. 页面展示摘要正文，并允许复制或下载。

## 5. 触发时机

建议把生成时机限制为“活动已结束后”或“管理员手动查看时”。

可采用两种模式：

1. 手动生成模式
   - 管理员在活动详情页点击按钮后生成。
   - 最容易落地，便于验证。

2. 自动生成模式
   - 当活动结束时间早于当前时间，且活动状态已关闭时自动返回摘要。
   - 若摘要暂未存储，则接口现算现出。

为了最小改造，建议第一版优先采用“手动生成模式 + 接口现算现出”。

## 6. 边界条件

1. 活动不存在
   - 返回 `404`，`{"detail": "activity not found"}`。

2. 活动尚未结束
   - 允许管理员查看，但摘要中的后续待办应标记为“活动未结束，摘要仅供预览”。

3. 没有报名记录
   - 报名人数为 `0`，缺席成员列表为空。

4. 没有签到记录
   - 签到人数为 `0`，后续待办中应提示“确认活动是否正常执行”。

5. 存在撤销签到
   - 撤销记录不计入有效签到。
   - 撤销原因可汇总为“签到异常说明”。

6. 活动数据缺失距离字段
   - 距离字段按 `0` 处理，不影响摘要生成。

7. 反馈文本为空
   - 反馈摘要回退为模板句，例如“活动已结束，建议补充现场反馈和照片”。

## 7. 验收标准

1. 接口返回 200 时，响应结构符合 `{"data": ..., "message": "成功"}`。
2. 活动不存在时，返回结构化错误 `{"detail": "activity not found"}`。
3. 报名人数、签到人数、缺席统计均可从现有数据源计算。
4. 摘要内容为全中文，面向管理员直接阅读。
5. 不与现有“提醒、候补、签到补签、撤销签到”语义重复。
6. 方案足够具体，开发者可以在一个 30 分钟会话内完成第一版接口。

## 8. 具体实施步骤

### 步骤一：确认数据口径

1. 读取活动详情接口，确认可拿到活动基础字段。
2. 读取报名记录，按活动 ID 统计报名人数。
3. 读取签到记录，过滤撤销签到，统计有效签到人数。
4. 根据成员表反查报名但未签到成员，生成缺席名单。
5. 将活动结束后的管理员总结文本作为反馈摘要来源。

### 步骤二：设计只读聚合函数

1. 新增一个聚合函数，输入活动 ID。
2. 查询活动基本信息。
3. 查询报名、签到、撤销签到数据。
4. 计算缺席成员与后续待办。
5. 组装统一的摘要对象。

### 步骤三：实现后端接口

1. 在 `backend/routes/activities.py` 中新增只读路由。
2. 复用现有权限校验，只允许管理员和团长访问。
3. 返回 `ApiResponse`，错误统一用 `HTTPException(detail=...)`。
4. 保持 SQL 参数化，避免字符串拼接。

### 步骤四：补前端入口

1. 在活动详情页增加摘要按钮。
2. 活动结束后高亮入口。
3. 展示摘要正文、缺席名单和待办事项。
4. 提供复制文本功能，方便管理员直接转发。

### 步骤五：补测试

1. 添加成功返回测试，确认 `data` 与 `message` 字段存在。
2. 添加活动不存在测试，确认返回 `404` 且 detail 结构正确。
3. 添加报名为空、签到为空、撤销签到存在的边界测试。
4. 添加权限测试，确认普通成员不可访问。

### 步骤六：验收与回归

1. 运行 `pytest -q`。
2. 手动请求接口，确认返回 200。
3. 检查 JSON 结构是否符合 `ApiResponse`。
4. 确认没有日志泄露敏感信息。

## 9. 推荐的第一版摘要模板

建议输出固定文案框架：

1. 活动基本信息
   - 活动名称、时间、地点、距离。

2. 参与统计
   - 报名人数、签到人数、签到率。

3. 缺席成员
   - 名单 + 人数。

4. 反馈摘要
   - 一段管理员可编辑的总结。

5. 后续待办
   - 2 到 5 条可执行事项。

6. 补充说明
   - 若活动未结束、数据不足或存在撤销签到，追加提示。

## 10. 结论

这套方案的核心是：不新增复杂写入链路，直接把活动、报名、签到、成员和任务数据聚合成一份只读摘要。这样既能快速落地，又能保证和现有的提醒、候补、签到补签、撤销机制互不冲突，适合作为第一版活动复盘能力上线。
