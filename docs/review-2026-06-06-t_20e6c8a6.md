# 代码审查报告
## 严重（必须修）
- [backend/routes/tasks.py:157-185] `batch_create_task_items` 直接接受 `raw_payload`，虽然后续做了 Pydantic 校验，但这里没有 `current_user` 和权限检查，导致任意匿名请求都能批量写入工作区任务；同时工作区路径只做了固定字符串比较，绕过成本低且可被别的路径入口复用 → 建议：补上 `current_user: CurrentUser = Depends(get_current_user)` 并在函数开头调用 `admin_or_leader(current_user)`；把工作区路径校验抽成统一白名单函数，不要在路由里手写固定路径比较。
- [backend/routes/tasks.py:175-177, 205-226] `workspace_path` 仅对单一仓库根路径做字符串相等判断，且 `import_task_items` 允许从请求体带入任意 `workspace_path` 后再调用 `upsert_workspace_task_item`；这会把写入范围和部署目录强耦合，后续一旦目录迁移或存在软链接就可能越界写入/读出错误 workspace → 建议：改成基于允许根目录集合的 `Path.resolve()` + `is_relative_to()` 校验，并统一在 repository 层重复校验，避免仅靠路由层约束。
- [backend/routes/app.py:52-59] `http_exception_handler` 会把 `exc.detail` 原样透传到响应体；如果下游把内部异常、数据库错误或用户输入直接塞进 `detail`，API 会对外泄漏实现细节和潜在敏感信息 → 建议：对外只返回固定格式与白名单消息，内部详情写日志，不直接回传原始 `detail`。

## 中等（应该修）
- [backend/routes/tasks.py:123-146, 188-226] 任务创建/导入接口对输入约束不一致：`TaskImportItem.status` 是自由字符串，`TaskItemCreate` 的状态集合与 `workspaces.py` 的 `VALID_TASK_STATUSES` 并不共享同一来源，后续容易出现 API、前端、数据库三套状态口径 → 建议：把状态枚举与字段长度约束集中到一个常量/模型里，所有路由复用同一份校验逻辑。
- [backend/routes/tasks.py:229-243, 246-259] `read_workspace_board` 和 `intake_worker` 直接把仓库返回的字典透给 API，没有对关键字段缺失或类型异常做兜底；一旦历史脏数据进入库中，接口更可能 500 而不是返回可诊断的 4xx/降级数据 → 建议：增加输出模型或显式字段检查，必要时对坏数据做过滤并记录告警。
- [backend/routes/common.py:36-50] `sanitize_member_payload` 里通过查询 `members` 表条数来放开“首个用户”任意角色的 bootstrap 逻辑，但函数同时又对非 `UserRegister` 对象强行回写 `ROLE_MEMBER`，请求语义被修改而不是拒绝；这类隐式改写很容易让调用方误以为自己的 role 生效 → 建议：把 bootstrap 逻辑限制在单独注册入口，并对非允许角色请求直接报错，不要在公共 sanitize 函数里静默改值。
- [backend/routes/members.py:36-40] `create_member_endpoint` 引入了 `hashlib, secrets` 但并未使用，且把 `password_hash` 直接置空再传给 `create_member`；如果 repository 没有再次强制哈希，这会导致空哈希或明文密码风险 → 建议：确认密码哈希只存在单一可信层（最好在 repository 或 service 层），路由层不要拼装 `password_hash` 占位字段。

## 建议（可以修）
- [backend/routes/announcements.py:18-21, 42-48] 公告创建/删除接口直接返回 503，但仍然保留了写接口签名和 payload 结构；如果这是临时下线，建议在路由层显式标注禁用原因并统一下线相关前端入口，避免客户端误以为接口可用。
- [backend/routes/activities.py:21-22, 66-71] `create_activity_endpoint` 和报名冲突分支都有用户可见中文错误文案，但活动读取接口对认证与授权没有同等梳理；如果活动应只对成员可见，建议补齐读权限策略，避免“写保护、读开放”的不一致。
- [backend/app.py:94-101, 129-136] 健康检查把 `stale_workspace_artifacts` 在多个分支重复返回，字段含义一致但命名和层级分散；如果这是给监控/前端消费的契约，建议抽成单一序列化函数，减少后续字段漂移。
