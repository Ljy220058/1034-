# 新手任务接力说明页

## 概述

本文档说明新加入协作者如何理解任务看板状态、查看任务关键信息，
并把一个空闲任务从接手推进到提交结果。

任务接力指的是：上一位协作者留下任务目标、工作区和验收标准，
下一位协作者根据这些信息继续完成交付。

适用对象：第一次参与 1034 跑团管理系统协作的协作者。
这包括文档、前端、后端、测试、评审和运维角色。

## 快速开始

先用下面的命令查看当前工作区任务列表，再按状态和负责人判断是否可以接手。

```bash
export BASE_URL='http://localhost:8000/api/v1'
export TOKEN='<替换为你的 token>'
export WORKSPACE_PATH='/root/autodl-tmp/projects/hermes-swarm-lab'

curl -sS "$BASE_URL/workspaces/tasks?workspace_path=$WORKSPACE_PATH&limit=20" \
  -H "Authorization: Bearer $TOKEN"
```

如果只想查看待办任务，可以加 `status=todo`。

```bash
curl -sS "$BASE_URL/workspaces/tasks?workspace_path=$WORKSPACE_PATH&status=todo&limit=20" \
  -H "Authorization: Bearer $TOKEN"
```

返回结果里优先看这几个字段：

```json
{
  "data": [
    {
      "task_id": "t_7c3d48c1",
      "title": "编写新手任务接力说明页",
      "status": "running",
      "updated_at": "2026-06-06T15:10:00+00:00",
      "assignee": "docs-writer",
      "workspace_path": "/root/autodl-tmp/projects/hermes-swarm-lab",
      "parent_task_id": null,
      "metadata": {}
    }
  ],
  "message": "成功"
}
```

## 任务状态说明

任务状态表示任务当前处在协作流程的哪个阶段。
新手接手任务前，应先判断状态是否允许继续推进。

### 待办

- 常见英文值：`todo`、`ready`
- 含义：任务已经创建，还没有人处理，或依赖已经完成等待接手。
- 处理方式：可以阅读任务说明，确认适合自己的能力后接手。

### 进行中

- 常见英文值：`running`、`doing`
- 含义：已经有协作者或 worker 正在处理。
- 处理方式：不要重复接手；先查看负责人和最近更新时间。

### 阻塞

- 常见英文值：`blocked`
- 含义：当前缺少权限、输入、上游结果或人工判断。
- 处理方式：不要盲目修改；先阅读阻塞原因和评论。

### 完成

- 常见英文值：`done`
- 含义：任务已经交付并记录结果。
- 处理方式：只用于学习参考；不要重新打开已完成任务。

`worker`（自动化工人）是执行任务的自动化协作者。
它通常有固定角色，例如 `docs-writer`、`backend-dev` 或 `reviewer`。

`status`（状态）是任务的机器可读阶段字段。界面会把它显示成中文，接口会返回英文值。

## 如何查看任务关键信息

接手任务前至少查看三类信息：负责人、工作区路径和验收标准。

### 1. 查看负责人

负责人表示当前任务由谁处理。字段通常叫 `assignee` 或 `owner`。

```bash
curl -sS "$BASE_URL/workspaces/tasks?workspace_path=$WORKSPACE_PATH&limit=20" \
  -H "Authorization: Bearer $TOKEN" | grep -E 'task_id|title|status|assignee'
```

判断方式：

- `assignee` 为空：通常表示还没有明确负责人，可以进入候选接手列表。
- `assignee` 是自己的角色：可以继续处理，但要先读任务说明。
- `assignee` 是别人：不要覆盖对方工作，除非任务已经被重新分配。

### 2. 查看工作区路径

工作区路径表示任务产物应该读写的位置。字段通常叫 `workspace_path`。

```bash
curl -sS "$BASE_URL/workspaces/tasks?workspace_path=$WORKSPACE_PATH&limit=20" \
  -H "Authorization: Bearer $TOKEN" | grep -E 'task_id|workspace_path'
```

本项目常用工作区是：

```text
/root/autodl-tmp/projects/hermes-swarm-lab
```

如果任务写的是 `dir:/root/autodl-tmp/projects/hermes-swarm-lab`，其中 `dir` 表示目录型工作区。
目录型工作区会长期保留文件，适合多人接力阅读和修改同一批文档。

注意：不要把文档写到临时目录里。
任务明确要求输出到 `docs/` 时，应使用工作区下的 `docs/` 目录。

### 3. 查看验收标准

验收标准说明任务完成后必须满足什么条件。
它可能出现在任务正文、评论、父任务交接信息或 `metadata`（元数据）字段中。

常见验收标准包括：

- 必须输出指定文件，例如 `docs/新手任务接力说明页.md`。
- 必须全中文，技术术语首次出现要解释。
- 必须包含步骤、示例和检查清单。
- 必须没有空白承诺、占位标题或未完成说明。
- 必须通过指定命令或人工检查。

建议把验收标准复制到自己的工作笔记中，并在提交前逐条打勾。

## 完整接力示例

下面示例演示从发现空闲任务到提交结果的完整过程。

### 第一步：查看待办任务

```bash
export BASE_URL='http://localhost:8000/api/v1'
export TOKEN='<替换为你的 token>'
export WORKSPACE_PATH='/root/autodl-tmp/projects/hermes-swarm-lab'

curl -sS "$BASE_URL/workspaces/tasks?workspace_path=$WORKSPACE_PATH&status=todo&limit=20" \
  -H "Authorization: Bearer $TOKEN"
```

重点检查返回里的 `task_id`、`title`、`assignee` 和 `workspace_path`。

### 第二步：判断是否适合接手

假设看到如下任务：

```json
{
  "task_id": "t_doc_example",
  "title": "补充活动报名用户指南",
  "status": "todo",
  "assignee": null,
  "workspace_path": "/root/autodl-tmp/projects/hermes-swarm-lab",
  "metadata": {
    "acceptance": [
      "输出到 docs/user-guide.md",
      "包含报名、取消报名和签到步骤",
      "没有未完成占位内容"
    ]
  }
}
```

这个任务没有负责人，状态是待办，工作区也在当前仓库内。文档协作者可以接手。

如果任务标题包含 `后端`、`数据库` 或 `接口实现`，文档协作者应交给后端协作者处理。

### 第三步：进入工作区

```bash
cd /root/autodl-tmp/projects/hermes-swarm-lab
```

进入工作区后，先读已有文档和相关代码。文档任务不要直接猜测接口或字段。

```bash
# 查看文档目录
find docs -maxdepth 1 -type f -name '*.md' | sort

# 查看项目总览
sed -n '1,160p' README.md
```

### 第四步：完成文档修改

按任务要求修改指定 Markdown（Markdown，轻量级标记文档）文件。

文档结构建议保持：

````markdown
# 标题

## 概述

一句话说明这份文档解决什么问题。

## 快速开始

```bash
可复制粘贴的命令
```

## 步骤说明

1. 第一步做什么。
2. 第二步看什么。
3. 第三步如何判断完成。

## 注意事项

- 写清楚限制和容易出错的地方。
```
````

### 第五步：提交前自检

```bash
grep -R "占位符\|未完成" docs/新手任务接力说明页.md || true
```

如果命令输出匹配行，说明还有未完成说明，需要先改成可执行内容。

再检查文件是否在任务要求的位置：

```bash
test -f docs/新手任务接力说明页.md && echo '文档文件存在'
```

### 第六步：记录结果

提交结果时，说明三件事：

1. 改了哪个文件。
2. 满足了哪些验收标准。
3. 用了哪些命令或人工检查。

结果示例：

```text
已完成 docs/新手任务接力说明页.md。
文档解释了待办、进行中、阻塞、完成四类状态。
文档补充了查看负责人、工作区路径和验收标准的方法。
已检查文档中没有未完成占位内容。
```

## 常见误区和处理建议

### 误区 1：只看任务标题就开始写

- 风险：容易漏掉输出路径、验收标准和限制条件。
- 建议：先读任务正文、评论、父任务交接信息和 `metadata`。

### 误区 2：看到 `running` 任务也接手

- 风险：可能和正在处理的人产生重复修改。
- 建议：先看 `assignee` 和更新时间；除非被重新分配，否则不要接手。

### 误区 3：把 `blocked` 当成普通失败

- 风险：会在缺少权限或输入时反复空跑。
- 建议：先读阻塞原因，确认缺什么，再交给对应负责人处理。

### 误区 4：不进入工作区就改文件

- 风险：文件可能写到错误目录，后续协作者找不到。
- 建议：先 `cd` 到 `workspace_path`，再读写相对路径。

### 误区 5：只写结论不写验证命令

- 风险：审核者无法复现你的判断。
- 建议：在结果里写清楚执行过的检查命令和输出摘要。

### 误区 6：文档里留下未完成占位内容

- 风险：新手会以为流程不完整。
- 建议：提交前搜索占位相关文字，并改成可执行说明。

### 误区 7：使用未验证的接口示例

- 风险：curl 命令复制后可能失败。
- 建议：接口文档先用本地服务或测试工具验证返回结构，再写入文档。

### 误区 8：忽略父任务交接信息

- 风险：可能重复做已经完成的部分。
- 建议：接手前阅读父任务摘要和评论，确认本任务边界。

### 误区 9：把产物放到工作区外

- 风险：后续任务和 README 链接无法直接引用。
- 建议：任务要求写入 `docs/` 时，只写入仓库内 `docs/`。

## 提交前检查清单

- [ ] 我已经确认任务状态是待办，或任务明确分配给我。
- [ ] 我已经查看负责人字段，没有覆盖他人的进行中任务。
- [ ] 我已经进入任务指定的工作区路径。
- [ ] 我已经阅读任务正文、评论和验收标准。
- [ ] 我已经把产物写到任务要求的文件路径。
- [ ] 我已经检查文档中没有未完成占位内容。
- [ ] 我已经在结果里写明文件路径、完成内容和验证方式。

## 注意事项

- 待办任务不一定都适合自己接手。先看任务类型，再看自己的角色能力。
- 进行中任务优先尊重当前负责人。需要协作时先留言，不要直接覆盖文件。
- 阻塞任务的重点是补齐缺失信息，不是重复执行同一操作。
- 完成任务可以作为参考，但不要把已完成任务重新当成待办任务处理。
- 文档任务只修改 `.md` 文件，不修改代码、配置、数据库迁移或测试文件。
