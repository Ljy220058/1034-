# 成员成长徽章体系方案

## 1. 方案目标

成员成长徽章体系用于把跑团成员在报名、签到、持续参与、资料完善、组织协作等行为转化为可见荣誉，鼓励成员形成稳定参与习惯，也方便团长和管理员快速识别活跃成员、可靠成员和潜在组织者。

本方案只做功能设计，不修改业务代码。方案优先复用现有成员、活动、报名、签到、公告和分析视图数据，不依赖第三方 API，不涉及 AI/LLM，不强制新增数据库表。首版可通过后端实时计算或轻量缓存实现。

## 2. 现有数据来源梳理

### 2.1 成员数据

来源表：`members`

可用字段：

| 字段 | 用途 |
|---|---|
| `id` | 成员唯一标识，徽章计算的主键 |
| `name` | 前端展示成员姓名 |
| `role` | 区分普通成员、团长、管理员；部分组织类徽章可限定角色或隐藏给普通成员 |
| `running_years` | 判断资料完整度、跑步经验展示 |
| `pace` | 判断资料完整度、活动配速匹配参考 |
| `usual_distance_km` | 判断资料完整度、训练偏好展示 |
| `training_goal` | 判断资料完整度、成长目标展示 |
| `created_at` | 可用于“新成员起步”类提示，但首版不建议作为核心徽章条件 |
| `updated_at` | 可用于资料最近更新时间提示 |

### 2.2 活动数据

来源表：`activities`

可用字段：

| 字段 | 用途 |
|---|---|
| `id` | 活动唯一标识 |
| `title` | 徽章明细中展示参与活动名 |
| `start_time` | 判断活动是否已结束、计算连续参与周期、统计本月/本年参与 |
| `location` | 未来可扩展地点类徽章；首版不作为核心条件 |
| `route` | 未来可扩展路线类徽章；首版不作为核心条件 |
| `distance_km` | 计算累计跑量、长距离挑战徽章 |
| `pace_group` | 未来可扩展配速组徽章；首版不作为核心条件 |
| `max_participants` | 与候补/满员场景相关，首版不参与徽章计算 |

### 2.3 报名数据

来源表：`registrations`

可用字段：

| 字段 | 用途 |
|---|---|
| `activity_id` | 关联活动 |
| `member_id` | 关联成员 |
| `status` | 判断报名成功或取消报名 |
| `created_at` | 计算报名次数、活动前报名、连续报名行为 |

注意：报名表有 `UNIQUE(activity_id, member_id)`，同一成员同一活动只保留一条报名状态。取消报名后状态为 `cancelled`，不应计入实际参与徽章。

### 2.4 签到数据

来源表：`attendances`

可用字段：

| 字段 | 用途 |
|---|---|
| `activity_id` | 关联活动 |
| `member_id` | 关联成员 |
| `status` | 判断是否已签到，首版只统计 `signed_in` |
| `signed_in_at` | 判断实际签到时间、连续参与周期 |
| `gps_checked` | 判断是否通过定位签到，可设计可信签到类徽章 |

注意：签到表同样有 `UNIQUE(activity_id, member_id)`，如果签到被撤销或改为缺席，应立即影响徽章。

### 2.5 参与分析视图

来源视图：`activity_participation_facts`

可用字段：

| 字段 | 用途 |
|---|---|
| `activity_id` | 活动维度统计 |
| `member_id` | 成员维度统计 |
| `activity_date` | 按天、周、月统计参与 |
| `registration_status` | 判断报名状态 |
| `attendance_status` | 判断签到状态 |
| `participation_status` | 统一判断参与状态，推荐优先使用 |
| `signed_in_at` | 计算签到时间和参与顺序 |
| `gps_checked` | 计算可信签到徽章 |
| `registered_at` | 计算报名行为 |
| `activity_start_time` | 计算周期、活动结束状态 |

推荐首版后端优先基于该视图计算报名、签到和参与类徽章，减少重复拼接 SQL。

### 2.6 反馈数据现状

任务要求包含反馈行为，但当前 README、用户指南、API 文档和数据模型中未看到已实现的反馈表或反馈接口。首版徽章体系中“反馈贡献”建议设计为预留徽章：

1. 如果后续已有反馈表，则接入 `feedbacks` 或等价表。
2. 如果短期不实现反馈功能，则该徽章前端显示为“即将开放”或后端不返回。
3. 不建议为了徽章体系单独新增反馈表，避免让徽章功能反向扩大业务范围。

## 3. 徽章分级与展示原则

### 3.1 徽章状态

每个徽章建议包含以下状态：

| 状态 | 含义 | 前端表现 |
|---|---|---|
| `earned` | 已获得 | 彩色徽章，可点击查看获得原因 |
| `in_progress` | 未获得但有进度 | 灰色徽章，展示进度条和下一步提示 |
| `locked` | 暂不可获得 | 灰色锁定态，适用于未开放反馈类徽章 |
| `revoked` | 曾获得但已撤销 | 默认不在成员主页展示，仅管理员详情可见 |

### 3.2 徽章字段建议

后端返回给前端的单个徽章建议结构：

```json
{
  "key": "steady_runner",
  "name": "稳定出勤者",
  "level": "silver",
  "status": "earned",
  "summary": "累计完成 5 次活动签到",
  "earned_at": "2026-06-06T08:30:00+08:00",
  "progress": {
    "current": 5,
    "target": 5,
    "unit": "次签到"
  },
  "reason": "已签到活动 5 次",
  "revoke_reason": null
}
```

### 3.3 等级建议

首版不强制做复杂等级，可以采用三档：

| 等级 | 文案 | 用途 |
|---|---|---|
| `bronze` | 铜 | 入门成就，容易获得 |
| `silver` | 银 | 稳定参与，体现持续性 |
| `gold` | 金 | 高价值行为，数量门槛更高 |

若开发量需要压缩，首版可以每类只做一个等级，把等级字段固定为 `bronze`。

## 4. 徽章类型设计

### 4.1 初次报名者

| 项目 | 内容 |
|---|---|
| 徽章 key | `first_registration` |
| 徽章名称 | 初次报名者 |
| 鼓励行为 | 鼓励新成员完成第一次活动报名 |
| 获得条件 | 成员至少存在 1 条 `registrations.status = 'registered'` 的报名记录 |
| 推荐 SQL 条件 | `COUNT(*) FILTER WHERE registration_status = 'registered' >= 1`，SQLite 可用 `SUM(CASE WHEN registration_status = 'registered' THEN 1 ELSE 0 END)` |
| 展示文案 | “迈出第一步：已成功报名 1 次跑团活动。” |
| 进度文案 | “报名任意 1 次活动即可获得。” |
| 撤销规则 | 如果该成员所有报名记录都变为 `cancelled`，撤销该徽章 |
| 边界条件 | 报名已取消不计入；未来活动也可计入，因为鼓励的是报名动作 |
| 优先级 | 高，适合首版实现 |

### 4.2 首次完赛签到

| 项目 | 内容 |
|---|---|
| 徽章 key | `first_checkin` |
| 徽章名称 | 首次完赛签到 |
| 鼓励行为 | 鼓励成员从报名走到实际参与和签到 |
| 获得条件 | 成员至少存在 1 条 `participation_status = 'signed_in'` 的记录 |
| 推荐 SQL 条件 | `SUM(CASE WHEN participation_status = 'signed_in' THEN 1 ELSE 0 END) >= 1` |
| 展示文案 | “完成第一次签到，欢迎正式加入跑团节奏。” |
| 进度文案 | “完成任意 1 次活动签到即可获得。” |
| 撤销规则 | 如果对应签到被撤销，且成员没有其他已签到记录，撤销该徽章 |
| 边界条件 | 补签成功后应计入；`absent` 不计入；仅报名未签到不计入 |
| 优先级 | 高，适合首版实现 |

### 4.3 稳定出勤者

| 项目 | 内容 |
|---|---|
| 徽章 key | `steady_runner` |
| 徽章名称 | 稳定出勤者 |
| 鼓励行为 | 鼓励持续签到，不只参加一次 |
| 获得条件 | 累计 `signed_in` 活动次数达到 5 次 |
| 推荐 SQL 条件 | `signed_in_count >= 5` |
| 展示文案 | “累计完成 5 次活动签到，跑团节奏逐渐稳定。” |
| 进度文案 | “已签到 {current}/5 次。” |
| 撤销规则 | 如果签到被撤销导致累计次数低于 5，撤销该徽章 |
| 边界条件 | 同一活动重复签到只算 1 次；补签算 1 次；取消报名但仍保留有效签到时以签到为准 |
| 优先级 | 高，适合首版实现 |

### 4.4 连续参与者

| 项目 | 内容 |
|---|---|
| 徽章 key | `continuous_runner` |
| 徽章名称 | 连续参与者 |
| 鼓励行为 | 鼓励成员连续多周参加活动 |
| 获得条件 | 在任意连续 4 个自然周中，每周至少有 1 次 `signed_in` 活动 |
| 推荐计算方式 | 后端取成员所有已签到活动的 `activity_date`，按 ISO 周去重，判断是否存在连续 4 个周序号 |
| 展示文案 | “连续 4 周保持出勤，训练习惯正在形成。” |
| 进度文案 | “当前连续参与 {current}/4 周。” |
| 撤销规则 | 徽章一旦获得不因后续中断撤销；但如果历史签到被撤销导致从未满足连续 4 周，则撤销 |
| 边界条件 | 一周多次签到只算 1 周；跨年周要使用 ISO 年 + ISO 周计算；补签按活动日期所在周计入 |
| 优先级 | 中，计算稍复杂但不需要新增表 |

### 4.5 累计跑量达人

| 项目 | 内容 |
|---|---|
| 徽章 key | `distance_collector` |
| 徽章名称 | 累计跑量达人 |
| 鼓励行为 | 鼓励成员持续参加有距离记录的活动 |
| 获得条件 | 成员已签到活动的 `distance_km` 累计达到 50 公里 |
| 推荐 SQL 条件 | `SUM(COALESCE(activities.distance_km, 0)) WHERE participation_status = 'signed_in' >= 50` |
| 展示文案 | “累计完成 50 公里跑团活动，脚步有迹可循。” |
| 进度文案 | “已累计 {current}/50 公里。” |
| 撤销规则 | 如果活动距离被改小、活动被删除或签到被撤销导致累计距离低于 50，撤销该徽章 |
| 边界条件 | `distance_km` 为空按 0 公里；距离为 0 的活动不增加进度；取消报名不计入 |
| 优先级 | 高，能复用现有跑量排行逻辑 |

### 4.6 资料完善者

| 项目 | 内容 |
|---|---|
| 徽章 key | `profile_complete` |
| 徽章名称 | 资料完善者 |
| 鼓励行为 | 鼓励成员补齐训练基础信息，方便团长安排活动 |
| 获得条件 | `running_years`、`pace`、`usual_distance_km`、`training_goal` 均有有效值 |
| 推荐判断 | `running_years >= 0` 且 `pace` 非空且 `usual_distance_km` 非空且 `training_goal` 非空 |
| 展示文案 | “训练资料已完善，团长能更好地安排适合你的活动。” |
| 进度文案 | “还差 {missing_fields} 项资料。” |
| 撤销规则 | 如果成员资料被清空导致任一必填项缺失，撤销该徽章 |
| 边界条件 | `running_years = 0` 对新手是有效值；空字符串和只含空格视为缺失；`usual_distance_km = 0` 不建议视为有效常跑距离 |
| 优先级 | 高，前后端实现都较轻 |

### 4.7 可信签到者

| 项目 | 内容 |
|---|---|
| 徽章 key | `trusted_checkin` |
| 徽章名称 | 可信签到者 |
| 鼓励行为 | 鼓励成员按规则完成定位签到 |
| 获得条件 | 累计 3 次 `signed_in` 且 `gps_checked = true` 的签到 |
| 推荐 SQL 条件 | `SUM(CASE WHEN participation_status = 'signed_in' AND gps_checked = 1 THEN 1 ELSE 0 END) >= 3` |
| 展示文案 | “已完成 3 次定位签到，活动记录更可信。” |
| 进度文案 | “已完成 {current}/3 次定位签到。” |
| 撤销规则 | 如果签到被撤销或 `gps_checked` 被更正为 false 导致次数低于 3，撤销该徽章 |
| 边界条件 | 如果某些活动不要求 GPS，不影响其他徽章；该徽章只统计有 GPS 校验的签到 |
| 优先级 | 中，适合在签到数据稳定后实现 |

### 4.8 活动组织助手

| 项目 | 内容 |
|---|---|
| 徽章 key | `activity_helper` |
| 徽章名称 | 活动组织助手 |
| 鼓励行为 | 鼓励团长、管理员或运营成员协助创建和维护活动 |
| 获得条件 | 首版缺少 `activities.created_by` 或类似字段，建议暂不自动发放；若后续补充创建者字段，则创建或维护 3 次活动后获得 |
| 推荐计算方式 | 后续基于 `activities.created_by = member_id` 或活动操作日志统计 |
| 展示文案 | “协助组织多次活动，是跑团稳定运转的幕后力量。” |
| 进度文案 | “活动组织记录接入后开放。” |
| 撤销规则 | 如果对应活动被删除或创建者记录被更正导致次数低于门槛，撤销该徽章 |
| 边界条件 | 当前系统无法可靠识别活动创建者，不建议用 `role` 直接发放，避免把管理员身份误当成组织贡献 |
| 优先级 | 低，作为预留徽章 |

### 4.9 反馈贡献者（预留）

| 项目 | 内容 |
|---|---|
| 徽章 key | `feedback_contributor` |
| 徽章名称 | 反馈贡献者 |
| 鼓励行为 | 鼓励成员在活动后提交复盘或建议 |
| 获得条件 | 当前未发现反馈数据源；后续若有反馈表，提交 3 条有效反馈后获得 |
| 推荐计算方式 | 后续基于 `feedbacks.member_id`、`feedbacks.activity_id`、`feedbacks.status = 'accepted'` 统计 |
| 展示文案 | “持续提供活动反馈，帮助跑团越办越好。” |
| 进度文案 | “反馈功能接入后开放。” |
| 撤销规则 | 如果反馈被删除、判定无效或成员撤回导致有效反馈少于 3 条，撤销该徽章 |
| 边界条件 | 不应把公告评论、系统备注或管理员代填内容直接算作成员反馈 |
| 优先级 | 低，除非反馈功能已实现 |

## 5. 前端展示位置

### 5.1 我的资料页

位置：当前用户查看个人信息的页面或“我的资料”模块。

展示内容：

1. 顶部展示已获得徽章数量，例如“已获得 4 枚徽章”。
2. 以 2 到 3 列卡片展示徽章。
3. 已获得徽章展示彩色图标、名称、获得文案和获得时间。
4. 未获得徽章展示灰色图标、进度条和下一步提示。
5. 预留徽章展示锁定态，不显示具体计算进度。

用户价值：成员能看到自己的参与成果和下一步目标。

### 5.2 成员列表页

位置：管理员和团长可访问的成员列表。

展示内容：

1. 每个成员行展示最多 3 枚代表性徽章。
2. 优先级建议：`distance_collector`、`steady_runner`、`continuous_runner`、`trusted_checkin`、`profile_complete`、`first_checkin`。
3. 鼠标悬停或点击展示徽章名称和获得原因。
4. 如果成员没有徽章，显示“暂无徽章”，不要留空造成误解。

用户价值：团长快速识别活跃成员、稳定出勤成员和资料完整成员。

### 5.3 成员详情页或抽屉

位置：成员列表点击成员后的详情区域。

展示内容：

1. 完整徽章墙。
2. 每个徽章的获得条件、当前进度、获得时间。
3. 管理员可见撤销说明和计算依据，例如“因签到撤销，当前进度 4/5”。

用户价值：便于解释为什么某成员获得或失去徽章。

### 5.4 活动详情页

位置：活动报名名单或签到名单区域。

展示内容：

1. 报名成员姓名旁展示 1 到 2 枚高价值徽章。
2. 签到名单中优先展示 `trusted_checkin` 和 `steady_runner`。
3. 不在活动详情页展示全部徽章，避免干扰报名和签到主流程。

用户价值：帮助组织者识别可靠参与者和活跃成员。

### 5.5 数据统计页面

位置：现有数据统计页面或后续跑量排行页面。

展示内容：

1. 在成员跑量排行中展示 `distance_collector`。
2. 增加“徽章分布”轻量统计，例如获得稳定出勤者的人数。
3. 首版不需要新增复杂图表，只展示数量卡片即可。

用户价值：运营人员可以观察激励机制是否带动参与。

## 6. 后端计算方式

### 6.1 推荐接口

建议新增只读接口，不修改现有核心接口结构。

#### 6.1.1 查询单个成员徽章

```http
GET /api/v1/members/{member_id}/badges
```

权限建议：

1. 普通成员只能查询自己的徽章。
2. 团长和管理员可以查询任意成员徽章。

返回建议：

```json
{
  "data": {
    "member_id": 1,
    "badges": [],
    "summary": {
      "earned_count": 4,
      "available_count": 7,
      "locked_count": 2
    }
  },
  "message": "成功"
}
```

#### 6.1.2 批量查询成员徽章摘要

```http
GET /api/v1/members/badges/summary?member_ids=1,2,3
```

用途：成员列表页避免逐个请求。

权限建议：仅团长和管理员可用。

返回建议：

```json
{
  "data": {
    "items": [
      {
        "member_id": 1,
        "earned_count": 4,
        "top_badges": [
          {"key": "steady_runner", "name": "稳定出勤者", "level": "silver"}
        ]
      }
    ]
  },
  "message": "成功"
}
```

### 6.2 实时计算方案

首版建议实时计算，不新增徽章持久化表。

步骤：

1. 查询成员基础资料。
2. 查询该成员在 `activity_participation_facts` 中的报名、签到、GPS、活动日期记录。
3. JOIN `activities` 获取 `distance_km`。
4. 在 Python 服务层组装统一的 `BadgeResult` 列表。
5. 每个徽章独立计算 `status`、`progress`、`reason` 和 `revoke_reason`。

优点：

1. 不需要新增数据库表。
2. 签到撤销、活动距离修改、报名取消后结果立即一致。
3. 开发量适中，适合 30 分钟到 1 小时的小任务拆分。

缺点：

1. 成员列表批量展示时可能多次查询。
2. 后续如果徽章很多，需要缓存或预计算。

### 6.3 批量计算优化

成员列表页建议使用批量接口，一次计算多个成员：

1. 接收 `member_ids`，限制最多 100 个。
2. 用一条 SQL 聚合报名数、签到数、GPS 签到数、累计距离。
3. 对连续周徽章可在 Python 中按成员分组计算。
4. 返回每个成员的 `earned_count` 和最多 3 个 `top_badges`。

### 6.4 示例聚合 SQL

```sql
SELECT
    f.member_id,
    SUM(CASE WHEN f.registration_status = 'registered' THEN 1 ELSE 0 END) AS registered_count,
    SUM(CASE WHEN f.participation_status = 'signed_in' THEN 1 ELSE 0 END) AS signed_in_count,
    SUM(CASE WHEN f.participation_status = 'signed_in' AND f.gps_checked = 1 THEN 1 ELSE 0 END) AS gps_signed_in_count,
    COALESCE(SUM(CASE WHEN f.participation_status = 'signed_in' THEN COALESCE(a.distance_km, 0) ELSE 0 END), 0) AS total_distance_km
FROM activity_participation_facts f
JOIN activities a ON a.id = f.activity_id
WHERE f.member_id IN (/* member ids */)
GROUP BY f.member_id;
```

SQLite 注意事项：

1. 不要直接拼接用户传入的 `member_ids`，应使用参数占位符。
2. `gps_checked` 可能是布尔或 0/1，统一按 1 判断。
3. `distance_km` 为空时按 0 处理。

## 7. 边界条件

### 7.1 报名相关

1. 已取消报名不计入“初次报名者”。
2. 同一活动重复报名因唯一约束不会产生多条有效记录。
3. 报名未来活动可以获得报名类徽章，但不能获得签到类和跑量类徽章。
4. 如果报名记录从 `registered` 改为 `cancelled`，相关报名类进度应下降。

### 7.2 签到相关

1. 只有 `participation_status = 'signed_in'` 计入出勤、连续参与和跑量。
2. 补签成功应计入所有签到相关徽章。
3. 签到撤销后应重新计算徽章。
4. `absent` 不计入任何正向徽章。
5. 同一活动只计一次签到。

### 7.3 活动相关

1. 活动被删除后，对应报名和签到因外键级联删除，徽章应自动重新计算。
2. 活动距离为空时按 0 公里计入。
3. 活动距离被修改后，累计跑量徽章应实时变化。
4. 连续参与按活动日期计算，不按签到补录时间计算。

### 7.4 成员资料相关

1. `running_years = 0` 是有效值，表示新手。
2. `pace`、`training_goal` 为空字符串或只含空格时视为缺失。
3. `usual_distance_km` 为空或小于等于 0 时不建议算作完整资料。
4. 成员被删除后无需保留徽章。

### 7.5 权限相关

1. 普通成员只能查看自己的完整徽章。
2. 普通成员不应看到其他成员的完整徽章明细。
3. 团长和管理员可查看成员列表中的徽章摘要和成员详情中的完整徽章。
4. 撤销原因属于管理信息，普通成员可看到“条件不满足”，管理员可看到具体计算字段。

### 7.6 预留徽章相关

1. 反馈贡献者在反馈数据源不存在时应返回 `locked` 或不返回。
2. 活动组织助手在缺少创建者字段时不应自动发放。
3. 不要为了展示徽章而伪造反馈或组织数据。

### 8.1 后端任务建议

标题：为成员徽章添加只读计算接口

## 9. 验收标准

### 9.1 文档验收

1. 文档全中文。
2. 至少包含 6 类可实现徽章。
3. 每类徽章包含获得条件、展示文案和撤销规则。
4. 明确现有数据来源和反馈数据缺口。
5. 明确前端展示位置、后端计算方式、边界条件和验收标准。

### 9.2 后端实现验收

1. `GET /api/v1/members/{member_id}/badges` 返回统一结构。
2. 普通成员只能访问自己的徽章，团长和管理员可访问任意成员徽章。
3. 已报名、已签到、GPS 签到、累计跑量、资料完整度能正确计算。
4. 取消报名、撤销签到、修改活动距离后重新请求能得到最新徽章状态。
5. 无反馈数据源时不返回虚假的反馈徽章。
6. 接口测试覆盖主要获得和撤销路径。

### 9.3 前端实现验收

1. 我的资料页能展示徽章墙。
2. 已获得徽章和未获得徽章有明显视觉区分。
3. 未获得徽章展示当前进度和下一步提示。
4. 成员列表最多展示 3 枚代表性徽章，不破坏现有列表布局。
5. 接口失败时展示“徽章暂时不可用”，不影响成员资料、活动报名和签到主流程。

### 9.4 产品效果验收

1. 新成员能清楚知道报名 1 次、签到 1 次即可获得入门徽章。
2. 老成员能通过出勤次数、累计跑量和连续参与看到长期贡献。
3. 团长能在成员列表快速识别稳定参与成员。
4. 徽章不会和现有成员管理、活动管理、公告、签到、统计页面重复，而是作为激励层补充。

## 10. 首版推荐范围

首版建议实现以下 6 个徽章：

1. 初次报名者
2. 首次完赛签到
3. 稳定出勤者
4. 累计跑量达人
5. 资料完善者
6. 可信签到者

暂不实现或仅锁定展示：

1. 连续参与者：可放入第二批，因为跨年连续周计算稍复杂。
2. 活动组织助手：等待活动创建者字段或操作日志。
3. 反馈贡献者：等待反馈数据源。

这样能保证首版开发量可控，且完整覆盖报名、签到、资料和跑量四类高价值行为。
