# 活动提醒智能摘要功能方案

## 1. 目标与定位

“活动提醒智能摘要”用于在活动开始前，帮助团长和管理员快速确认活动准备情况。功能不依赖第三方服务，也不引入 AI 或大模型，而是基于系统已有的活动、报名、签到和成员数据，按固定规则生成一段中文管理摘要。

预期效果：管理员打开活动详情或活动列表中的“提醒摘要”入口后，可以一眼看到活动时间、地点、报名人数、签到风险和待办事项，减少活动前手工核对报名与签到状态的成本。

## 2. 现有代码与页面依据

本方案基于以下已实现能力设计：

- 活动接口：`backend/routes/activities.py`
  - `GET /api/v1/activities` 返回活动列表。
  - `GET /api/v1/activities/{activity_id}` 返回单个活动详情。
  - `POST /api/v1/activities/{activity_id}/registrations` 创建报名。
  - `DELETE /api/v1/activities/{activity_id}/registrations/{member_id}` 取消报名。
- 签到接口：`backend/routes/checkins.py`
  - `GET /api/v1/activities/{activity_id}/checkins` 返回某场活动签到记录。
  - `POST /api/v1/activities/{activity_id}/checkins` 创建普通签到。
- 数据访问：`backend/repository.py`
  - `list_activities()`、`get_activity()` 已能读取活动基础信息。
  - `create_registration()`、`cancel_registration()` 已维护报名状态。
  - `list_activity_attendance()` 已能读取某活动签到记录。
- 数据模型：`backend/models.py`
  - `Activity` 包含 `title`、`start_time`、`location`、`route`、`distance_km`、`pace_group`、`description`。
  - `Registration` 包含 `activity_id`、`member_id`、`status`。
  - `Attendance` 包含 `activity_id`、`member_id`、`status`、`signed_in_at`、`gps_checked`。
- 前端入口：`frontend/index.html` 与 `frontend/attendance.js`
  - 当前已有出勤签到面板，可输入活动 ID 后查看出勤记录。
  - 可在活动相关区域增加“生成提醒摘要”按钮和摘要卡片。

## 3. 最小可落地范围

### 3.1 数据来源

最小版本只使用现有数据库表，不新增数据库表：

1. `activities`：活动标题、开始时间、地点、路线、距离、配速组、描述。
2. `registrations`：统计 `status = 'registered'` 的报名人数。
3. `attendances`：统计 `status = 'signed_in'` 的已签到人数、未通过 GPS 校验人数。
4. `members`：可选读取报名成员姓名，用于后续展示“未签到名单”；最小版本可先不返回成员明细，只返回数量。

### 3.2 触发时机

最小版本不做后台定时任务，避免引入额外运行时复杂度。触发方式为：

- 管理员或团长在前端活动详情或出勤签到面板点击“生成提醒摘要”。
- 前端调用后端摘要接口，后端即时查询数据库并返回规则化摘要。
- 活动开始前任意时间都可生成；距离活动开始不足 1 小时时，在摘要中标记为“临近开始”。

后续如需要自动提醒，可再扩展为定时任务或公告草稿生成，但不属于本次最小版本。

### 3.3 展示位置

推荐先放在现有出勤签到视图附近：

- 在 `frontend/index.html` 的“出勤签到”区域增加“活动提醒摘要”卡片。
- 卡片包含：活动 ID 输入框共用现有控件、一个“生成提醒摘要”按钮、一个只读摘要展示区域。
- 在活动列表页或活动详情页成熟后，再把入口移动到单个活动卡片中。

## 4. 后端接口设计

### 4.1 新增接口

建议新增接口：

```http
GET /api/v1/activities/{activity_id}/reminder-summary
```

权限：仅 `admin` 和 `leader` 可访问。

原因：摘要包含报名和签到风险，属于活动管理信息，不应对普通成员开放。

### 4.2 返回结构

返回仍使用现有 `ApiResponse` 包装：

```json
{
  "data": {
    "activity_id": 10,
    "summary": "周六晨跑将于 2026-06-08 07:00 在人民公园东门开始，当前报名 18 人，已签到 0 人。活动距离开始不足 1 小时，请确认集合地点、路线说明和补签安排。",
    "metrics": {
      "registered_count": 18,
      "signed_in_count": 0,
      "not_signed_in_count": 18,
      "gps_unverified_count": 0,
      "starts_in_minutes": 55
    },
    "todos": [
      "确认集合地点是否仍为人民公园东门",
      "活动开始前提醒 18 名报名成员完成签到",
      "检查路线说明是否清晰"
    ],
    "risk_level": "warning"
  },
  "message": "成功"
}
```

### 4.3 字段说明

- `summary`：适合直接发给管理员的中文摘要，后端按固定模板生成。
- `metrics.registered_count`：当前有效报名人数。
- `metrics.signed_in_count`：当前已签到人数。
- `metrics.not_signed_in_count`：报名但未签到人数。
- `metrics.gps_unverified_count`：已签到但 GPS 未校验通过的人数。
- `metrics.starts_in_minutes`：距离活动开始的分钟数；已开始则可为负数。
- `todos`：基于规则生成的待办事项。
- `risk_level`：`normal`、`warning`、`danger` 三档。

### 4.4 后端实现建议

建议新增或修改以下文件：

- 修改 `backend/models.py`
  - 新增 `ActivityReminderSummaryOut`、`ActivityReminderMetrics` 等响应模型，也可以先用字典返回以降低改动量。
- 修改 `backend/repository.py`
  - 新增 `get_activity_registration_count(activity_id: int)`。
  - 新增 `get_activity_signed_in_count(activity_id: int)`。
  - 新增 `get_activity_gps_unverified_count(activity_id: int)`。
  - 如需减少查询次数，可新增一个聚合函数 `get_activity_reminder_metrics(activity_id: int)`。
- 修改 `backend/routes/activities.py`
  - 新增 `GET /{activity_id}/reminder-summary` 路由。
  - 调用 `admin_or_leader(current_user)` 做权限校验。
  - 活动不存在时返回 `404 activity not found`。
- 新增测试 `tests/test_activity_reminder_summary.py`
  - 覆盖活动不存在、普通成员无权限、无报名、已有报名、已有签到、临近开始等场景。

## 5. 前端入口设计

### 5.1 页面位置

最小版本放在 `frontend/index.html` 的“出勤签到”区域中，靠近活动 ID 输入框。原因是：

- 该区域已经要求用户输入活动 ID。
- 管理员查看签到记录时，正好也是生成提醒摘要的主要场景。
- 不需要先重做活动列表或详情页。

### 5.2 前端交互

新增一个摘要卡片：

- 标题：`活动提醒摘要`
- 操作按钮：`生成摘要`
- 状态：加载中、生成成功、无活动、网络错误
- 内容：显示后端返回的 `summary`、报名/签到数量和待办事项列表

### 5.3 前端 API 方法

在 `frontend/api.js` 的 `createApiClient()` 中新增：

```js
getActivityReminderSummary(activityId, options = {}) {
  return request(`/activities/${encodeURIComponent(activityId)}/reminder-summary`, {
    token: options.token,
  });
}
```

可在 `frontend/attendance.js` 中复用活动 ID 和 token 输入框，新增 `bootstrapReminderSummaryPanel()`，或先并入现有 `bootstrapAttendancePanel()`。

## 6. 摘要生成规则

### 6.1 风险等级

建议规则如下：

- `danger`
  - 活动已开始，但报名人数大于 0 且已签到人数为 0。
  - 或活动开始前 30 分钟内，未签到人数大于报名人数的 80%。
- `warning`
  - 活动开始前 1 小时内，未签到人数大于 0。
  - 或存在 GPS 未校验的签到记录。
  - 或活动缺少路线、距离、配速组等关键信息。
- `normal`
  - 有报名、有活动基础信息，且未发现上述风险。

### 6.2 待办事项规则

后端可按以下规则生成 `todos`：

1. 活动缺少 `route`：加入“补充路线说明”。
2. 活动缺少 `distance_km`：加入“补充活动距离”。
3. 活动缺少 `pace_group`：加入“确认配速分组”。
4. `registered_count == 0`：加入“确认是否需要发布报名提醒”。
5. `not_signed_in_count > 0` 且距离开始不足 60 分钟：加入“提醒未签到成员尽快完成签到”。
6. `gps_unverified_count > 0`：加入“复核未通过 GPS 校验的签到记录”。
7. 活动已开始且未签到人数仍大于 0：加入“活动开始后核对缺勤或补签情况”。

### 6.3 摘要模板

建议模板：

```text
{活动标题} 将于 {开始时间} 在 {地点} 开始，当前报名 {报名人数} 人，已签到 {签到人数} 人，仍有 {未签到人数} 人未签到。{风险说明}{待办摘要}
```

示例：

```text
周六晨跑将于 2026-06-08 07:00 在人民公园东门开始，当前报名 18 人，已签到 2 人，仍有 16 人未签到。活动距离开始不足 1 小时，请提醒报名成员完成签到，并确认路线和配速分组是否已说明清楚。
```

## 7. 边界条件

1. 活动不存在：返回 `404 activity not found`。
2. 当前用户不是管理员或团长：返回 `403 forbidden`。
3. 活动没有报名：摘要显示“当前暂无报名成员”，待办提示“确认是否需要发布报名提醒”。
4. 活动已经结束或开始时间早于当前时间：摘要显示“活动已开始/已过开始时间”，风险按签到情况提升。
5. 活动缺少路线、距离、配速组：不阻塞生成摘要，但加入待办事项。
6. 报名被取消：只统计 `status = 'registered'` 的报名记录。
7. 签到记录被撤销：只统计 `status = 'signed_in'` 的签到记录。
8. GPS 未校验：不否定签到结果，但在 `gps_unverified_count` 中统计，并加入待办提示。
9. 数据库里没有签到表或历史迁移未完成：接口应跟随现有初始化流程，测试覆盖迁移后正常读取。
10. 时间字段无时区：沿用现有 `_parse_dt()` 处理逻辑，将无时区时间按 UTC 或现有约定补齐。

## 8. 具体实现步骤

1. 在 `backend/repository.py` 增加活动提醒摘要所需的聚合查询函数，输入 `activity_id`，输出报名人数、签到人数、GPS 未校验人数和活动基础信息。
2. 在 `backend/routes/activities.py` 增加 `GET /api/v1/activities/{activity_id}/reminder-summary` 路由，校验 `admin_or_leader(current_user)`，活动不存在时返回 404。
3. 在后端实现规则函数，例如 `_build_activity_reminder_summary(activity, metrics, now)`，统一生成 `summary`、`todos` 和 `risk_level`，避免把模板逻辑散落在路由里。
4. 新增 `tests/test_activity_reminder_summary.py`，至少覆盖：无权限、活动不存在、无报名、临近开始且未签到、GPS 未校验、活动信息缺失六类场景。
5. 在 `frontend/api.js` 增加 `getActivityReminderSummary(activityId, options)` 方法，复用现有请求封装和 token 传递方式。
6. 在 `frontend/index.html` 的出勤签到区域增加摘要卡片容器、按钮和展示区域，移动端保持单列布局，不引入横向滚动。
7. 在 `frontend/attendance.js` 增加生成摘要的事件处理逻辑，点击按钮后读取活动 ID 和 token，展示加载中、成功、错误和空态。
8. 更新 `docs/api.md`，补充新接口路径、权限、返回示例、错误码和字段说明。
9. 更新 `docs/user-guide.md`，在团长和管理员使用流程中加入“活动开始前生成提醒摘要”的说明。
10. 运行后端测试与前端相关静态测试，确认新增接口和页面交互不影响现有报名、签到与任务板功能。

## 9. 验收标准

1. 管理员或团长访问 `GET /api/v1/activities/{activity_id}/reminder-summary` 能获得中文摘要、统计指标、待办事项和风险等级。
2. 普通成员访问该接口返回 `403 forbidden`。
3. 活动不存在时返回 `404 activity not found`。
4. 当活动没有报名时，摘要明确显示暂无报名，并给出报名提醒待办。
5. 当活动开始前 1 小时内仍有人未签到时，摘要包含未签到风险提示。
6. 当存在 GPS 未校验的签到记录时，摘要包含 GPS 复核待办。
7. 前端出勤签到区域能通过活动 ID 生成摘要，并展示加载中、成功、错误和空态。
8. 移动端摘要卡片不产生横向滚动，按钮和文本可正常阅读。
9. 不新增数据库表，不依赖第三方 API，不使用 AI 或 LLM 服务。
10. 后端测试新增并通过，现有活动、报名、签到接口测试不回退。

## 10. 不纳入本次范围

- 不做短信、微信、邮件等外部通知。
- 不新增后台定时任务。
- 不自动发布公告。
- 不生成面向普通成员的个性化提醒。
- 不新增数据库表保存摘要历史。
- 不引入 AI、大模型或第三方摘要服务。

## 11. 推荐后续拆分任务

如果后续进入开发，可拆成两个小任务：

1. 后端任务：为活动新增提醒摘要接口，基于活动、报名和签到数据返回中文摘要。
2. 前端任务：在出勤签到区域增加活动提醒摘要卡片，支持生成、加载、错误和空态展示。
