# 训练完成智能复盘卡片数据契约

日期：2026-06-06
状态：最小可用契约
适用范围：后端训练复盘计算结果 → 前端“训练完成智能复盘卡片”展示
契约版本：training_review_card.v1

## 一、现有模型与文档依据

本契约基于当前仓库中已经存在的活动、成员、训练模板和跑步数据导入契约整理，不新增线上配置，不要求立即落库。

已查阅依据：

| 路径 | 相关内容 | 对本契约的影响 |
|---|---|---|
| `backend/models.py` | `MemberBase`、`ActivityBase`、`AttendanceCreate` 等 Pydantic 模型 | 成员 ID、活动距离、成员训练目标、GPS 签到状态是现有可用来源 |
| `backend/database.py` | `members`、`activities`、`registrations`、`attendances`、`announcements` 表 | 当前没有正式训练计划表或跑步记录表，本契约只定义后端计算结果结构 |
| `backend/routes/running_data_imports.py` | 跑步导入字段：`distance_km`、`duration_seconds`、`pace`、`location` | 实际距离、训练用时、导入来源和重复识别可作为后端计算来源 |
| `backend/running_data_anomaly_precheck.py` | 异常类型：缺失时间、异常配速、重复轨迹、超长距离、空GPS点 | 异常标签枚举沿用现有中文业务语义 |
| `frontend/training-templates.js` | 5K、10K、半马、全马训练模板及 `goal` 字段 | 计划目标可来自模板目标或成员个人训练目标 |
| `docs/训练计划日历导出联调样例.md` | 训练活动字段和日历导出输入约定 | 训练计划侧字段需要保持中文、时间和活动字段稳定 |

## 二、实体关系口径

当前仓库里的最小实体关系如下：

- `members`：跑团成员。可提供 `member_id`、成员常用配速、常用距离、个人训练目标。
- `activities`：跑团活动或训练活动。可提供活动标题、开始时间、目标距离、配速组。
- `attendances`：活动签到。可提供成员是否签到、是否完成 GPS 校验。
- 跑步导入向导：目前不是正式落库表，但接口契约已经稳定暴露实际距离、用时、GPS 轨迹摘要等字段。
- 训练模板：目前是前端静态模板，可作为计划目标和预期距离的候选来源。

因此，“训练完成智能复盘卡片”不直接等同某一张现有表，而是后端在训练完成后根据成员、活动/训练计划、跑步导入记录和异常预检结果计算出的展示 DTO（数据传输对象）。

## 四、字段明细

| 字段 | 类型 | 必填 | 来源 | 缺失时降级策略 |
|---|---|---:|---|---|
| `contract_version` | string | 是 | 后端常量 | 不允许缺失；缺失时前端应拒绝渲染并提示“复盘数据版本缺失” |
| `training_id` | string | 是 | 优先活动 ID（`activities.id`），未来可替换为训练计划 ID | 不允许缺失；缺失时后端不生成复盘卡片 |
| `member_id` | integer | 是 | `members.id` | 不允许缺失；缺失时后端不生成复盘卡片 |
| `plan_goal` | object | 是 | 训练模板、活动字段、成员目标综合生成 | 若缺少计划目标，仍返回对象，但 `goal_text` 使用“未设置明确训练目标”，目标距离从活动距离或实际距离兜底 |
| `plan_goal.goal_text` | string | 是 | `frontend/training-templates.js` 的 `goal`、`members.training_goal`、`activities.description` | 缺失时返回“未设置明确训练目标”，前端展示弱提示 |
| `plan_goal.target_distance_km` | number 或 null | 是 | `activities.distance_km`、训练模板距离、成员常用距离 | 缺失时为 `null`；完成率无法按目标距离计算时降级为 `completion_rate=null` |
| `plan_goal.target_pace_seconds_per_km` | integer 或 null | 是 | 活动配速组、成员常用配速、训练模板目标 | 缺失时为 `null`；建议文案不比较目标配速，只描述实际配速 |
| `plan_goal.source` | enum string | 是 | 后端计算 | 可选值：`activity`、`training_template`、`member_profile`、`fallback`；缺失时使用 `fallback` |
| `actual_distance_km` | number 或 null | 是 | 跑步导入预览 `distance_km`、GPS 轨迹计算、手工补录 | 缺失 GPS 但有导入距离时继续使用导入距离；都缺失时为 `null` 并打 `距离缺失` 标签 |
| `duration_seconds` | integer 或 null | 是 | 跑步导入预览 `duration_seconds`、活动签到/手工补录 | 缺失时为 `null`；平均配速降级为 `null` 并打 `用时缺失` 标签 |
| `average_pace_seconds_per_km` | integer 或 null | 是 | 后端用 `duration_seconds / actual_distance_km` 计算 | 距离或用时缺失、距离为 0 时为 `null`，前端显示“配速暂不可用” |
| `completion_rate` | number 或 null | 是 | 后端用 `actual_distance_km / target_distance_km` 计算 | 目标距离或实际距离缺失、目标距离为 0 时为 `null`，前端显示“完成率暂不可用” |
| `completion_status` | enum string | 是 | 后端根据完成率和异常判断 | 可选值：`completed`、`partial`、`not_completed`、`unknown`；无法判断时为 `unknown` |
| `anomaly_tags` | array<string> | 是 | `backend/running_data_anomaly_precheck.py`、GPS/距离/用时降级结果 | 无异常时必须返回 `["无异常"]`；不得返回空数组，避免前端空态歧义 |
| `recommendation_text` | string | 是 | 后端规则生成或智能文案生成 | 智能文案失败时使用模板文案：“本次训练已记录，建议根据身体状态安排恢复。” |
| `data_quality` | object | 是 | 后端计算 | 缺失时后端补齐保守值：GPS unknown、来源 fallback、degraded=true |
| `data_quality.gps_status` | enum string | 是 | GPS 轨迹、签到 GPS 校验、导入异常预检 | 可选值：`available`、`missing`、`empty`、`not_required`、`unknown`；缺失时为 `unknown` |
| `data_quality.distance_source` | enum string | 是 | 后端距离选择逻辑 | 可选值：`gps_track`、`import_file`、`manual`、`activity_plan`、`unknown`；缺失时为 `unknown` |
| `data_quality.pace_source` | enum string | 是 | 后端配速选择逻辑 | 可选值：`duration_and_distance`、`import_file`、`manual`、`unknown`；缺失时为 `unknown` |
| `data_quality.degraded` | boolean | 是 | 后端降级判断 | 缺失时视为 `true`，前端展示“数据不完整”提示 |
| `data_quality.degrade_reason` | string 或 null | 是 | 后端降级判断 | 无降级时为 `null`；降级但原因缺失时返回“数据来源不完整” |
| `generated_at` | datetime string | 是 | 后端生成时间，ISO 8601 UTC | 不允许缺失；缺失时前端不展示“生成时间”，但记录告警 |

## 五、枚举约定

### `completion_status`

| 值 | 中文说明 | 建议判定口径 |
|---|---|---|
| `completed` | 已完成 | `completion_rate >= 1.0`，且没有阻断级异常 |
| `partial` | 部分完成 | `0 < completion_rate < 1.0` |
| `not_completed` | 未完成 | `actual_distance_km` 为 0，或签到后没有有效跑步记录 |
| `unknown` | 无法判断 | 目标距离或实际距离缺失，无法计算完成率 |

### `anomaly_tags`

最小可用标签建议：

- `无异常`
- `缺失时间`
- `异常配速`
- `重复轨迹`
- `超长距离`
- `空GPS点`
- `GPS缺失`
- `距离缺失`
- `用时缺失`
- `目标缺失`
- `未完成训练`

标签必须使用中文，方便前端直接展示；若后续需要国际化，可再增加稳定的英文 code 字段，但 v1 不强制。

## 七、最小验证方式

本仓库同时提供 JSON Schema 和零依赖示例校验脚本：

- Schema：`schemas/training_review_card.schema.json`
- 校验脚本：`scripts/validate_training_review_samples.js`

建议验证命令：

```bash
node scripts/validate_training_review_samples.js
```

通过标准：命令输出 `训练复盘样例校验通过：3 条`，且退出码为 0。

## 八、后续落库建议

当前任务只定义数据契约，不新增数据库表。若后续需要持久化复盘结果，建议新增独立表 `training_review_cards`，并保持如下原则：

- `training_id`、`member_id` 建联合唯一约束，避免同一成员同一训练重复生成多张活跃复盘卡。
- `member_id` 外键引用 `members(id)` 并建立索引。
- 若 `training_id` 继续复用 `activities.id`，应显式声明 `FOREIGN KEY(training_id) REFERENCES activities(id)`；若未来训练计划独立成表，再迁移到正式训练计划表。
- `anomaly_tags` 和 `data_quality` 可在 SQLite 中用 TEXT 保存 JSON，但需要在应用层严格按本契约校验。
- 所有迁移必须提供回滚脚本，并用事务包裹。
