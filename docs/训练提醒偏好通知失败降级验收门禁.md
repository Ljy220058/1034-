# 训练提醒偏好通知失败降级验收门禁

## 一、适用范围

本文档用于验收“训练提醒偏好”相关实现前后的通知失败降级能力，重点检查短信、站内信、邮件和移动端推送等渠道不可用时，系统是否仍能给成员、管理员和测试人员提供可理解、可追踪、不过度打扰且不泄露隐私的中文处理结果。

本门禁只新增验收口径和检查清单，不新增接口、数据库表、消息队列或移动端实现；不依赖外部网络；不阻塞正在运行的实现任务。

## 二、现有依据与用户路径

已阅读并参考以下现有资料：

1. `docs/training_reminder_preferences_acceptance_checklist.md`：已有训练提醒偏好验收清单，覆盖默认状态、提前提醒、免打扰、渠道缺失、训练取消、重复提醒、隐私提示和移动端文案。
2. `docs/训练异常提醒规则配置样例.md`：已有异常提醒规则样例，覆盖配速突变、距离异常、心率缺失、重复上传、训练未完成、连续缺席和导入来源异常等提醒语义。
3. `docs/training_plan_completion_quality_gate.md`：已有训练计划完成率门禁，说明训练计划、每日目标、打卡、缺席和补签记录的基础质量要求。
4. 任务描述中的活动报名、训练取消、管理员群发、免打扰冲突、重复提醒和隐私提示要求。

通知失败可能影响的用户路径如下：

| 用户路径 | 失败影响 | 必须验收的降级结果 |
|---|---|---|
| 成员首次开启训练提醒 | 渠道未绑定或授权失败导致以为已开启但实际收不到 | 明确提示可用渠道和不可用原因，不把失败状态显示为成功 |
| 成员报名跑团活动 | 报名成功后训练前提醒无法发送 | 保留站内可见状态或提示补充渠道，避免成员错过集合信息 |
| 成员设置免打扰时段 | 提醒时间与免打扰冲突 | 按策略延后、提前或仅站内留存，并在偏好页说明 |
| 成员取消报名或训练取消 | 已排队提醒未取消 | 不再发送原训练提醒，必要时发送取消通知或站内说明 |
| 后台任务重试 | 同一提醒被重复推送 | 通过去重键和发送记录确保只触达一次 |
| 成员关闭提醒 | 旧队列继续发送 | 待发送提醒必须取消或失效，并给出关闭确认 |
| 管理员群发训练通知 | 误选人群或跨活动触达 | 群发前二次确认范围，失败时提供审计而非重复补发 |
| 异常提醒和复盘入口 | 数据异常触发提醒但渠道失败 | 只能展示保守中文提示，不给医疗判断，不泄露原始轨迹 |
| 移动端查看通知 | 文案过长或不可操作 | 标题和正文短句中文，失败和降级状态可读 |
| 普通成员访问偏好 | 读取或修改他人提醒设置 | 权限拒绝且不返回他人联系方式或提醒内容 |

## 三、门禁总原则

1. 通知失败不能静默吞掉。用户侧至少应看到可理解的偏好状态或站内说明，内部应保留可审计记录。
2. 降级不能越权。短信、邮件、移动推送不可用时，可以降级到站内信或页面提示，但不能把提醒发给管理员、团长或其他成员代收。
3. 免打扰优先级高于普通训练提醒。任何降级策略都不能绕过成员明确设置的免打扰时段。
4. 取消和关闭优先级高于重试。训练取消、成员取消报名或成员关闭提醒后，旧提醒不得因为失败重试再次触达。
5. 去重优先级高于补偿发送。后台任务重试、渠道切换和手工补发都必须复用同一业务去重口径。
6. 隐私优先。通知正文、失败提示、审计记录和管理员界面都不得暴露完整手机号、完整邮箱、访问令牌、原始定位轨迹或其他成员训练详情。
7. 移动端优先读懂。降级文案应短、准、可操作，不依赖长段说明才能理解下一步。

## 四、验收检查项

### 1. 短信渠道缺失时必须提示可用替代路径

通过标准：成员未绑定手机号、手机号格式无效或短信能力不可用时，系统不得显示“短信提醒已开启”。如果站内信或邮件仍可用，应提示“短信不可用，已改用站内提醒”或同等中文说明；如果没有任何可用渠道，应提示成员先补充通知方式。

失败示例：成员没有手机号，偏好页仍显示短信开关为开启；短信发送失败后只在日志里记录英文错误，用户界面仍显示提醒成功；系统把短信失败提醒发给团长代为转达。

建议验证方式：使用无手机号、异常手机号、短信服务返回失败三类样例，检查偏好页状态、发送记录、站内提示和失败审计；确认手机号只以脱敏形式出现在内部记录中。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer、security-reviewer。

### 2. 站内信不可用时不能假装兜底成功

通过标准：站内信存储、未读计数或消息中心不可用时，系统不能把站内信作为成功降级渠道。若还有邮件或移动推送可用，应清晰展示实际使用的渠道；若无可用渠道，应把训练提醒状态标记为待补充通知方式。

失败示例：站内信写入失败但接口仍返回“已发送”；用户看不到任何提醒，管理员页面却显示站内信成功；未读计数异常导致重复创建多条站内消息。

建议验证方式：模拟站内信写入失败、未读计数失败和消息中心关闭，检查接口返回、页面状态和审计记录；确认不会生成重复站内信。

适合跟进的 worker：backend-dev、test-engineer。

### 3. 邮件渠道缺失或退信时必须降级并脱敏

通过标准：成员邮箱缺失、邮箱格式无效或邮件退信时，系统应使用仍可用的站内信或移动推送提示，并在偏好页展示“邮件不可用”类中文状态。任何用户可见位置不得展示完整邮箱地址。

失败示例：退信后继续反复发送同一封训练提醒；页面展示完整邮箱和退信详情；邮件失败导致整个训练提醒偏好保存失败，但没有说明可用替代渠道。

建议验证方式：构造无邮箱、错误邮箱、退信回调和邮件服务暂不可用样例，检查降级状态、重试次数、中文提示和邮箱脱敏。

适合跟进的 worker：backend-dev、frontend-dev、security-reviewer、test-engineer。

### 4. 免打扰时段冲突必须优先处理

通过标准：训练提醒触发时间落入成员免打扰时段时，系统必须按产品策略延后、提前或仅保留站内未读提示，并在偏好页或提醒设置中说明该策略。降级到短信、邮件或移动推送时也必须遵守免打扰。

失败示例：成员设置晚上十点到早上七点免打扰，短信失败后补偿邮件在凌晨发送；推送被免打扰拦截后后台不断重试；提醒被丢弃但页面没有任何说明。

建议验证方式：构造跨午夜免打扰、全天免打扰、本地时区变化和训练开始前十分钟提醒样例，检查实际发送时间、待发送队列和中文说明。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer。

### 5. 训练取消后仍提醒必须被阻断

通过标准：活动取消、训练计划删除、成员取消报名或管理员移除成员后，原训练前提醒必须取消、失效或转换为取消通知。任何渠道失败重试都不能重新发送“训练即将开始”。

失败示例：成员取消报名后仍收到训练前十分钟短信；活动取消后移动端仍显示原地点集合；取消通知发送失败后，系统又补发原训练提醒。

建议验证方式：创建报名成功后的待发送提醒，再分别执行成员取消报名、管理员取消活动、训练计划删除和成员被移除，断言旧提醒不再触达，取消说明准确。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer。

### 6. 重复推送必须有业务去重键

通过标准：同一成员、同一训练或活动、同一提醒类型、同一触发时间只能产生一条有效提醒。后台任务重试、页面重复保存、渠道失败后补偿发送和管理员手工补发都必须复用同一去重口径。

失败示例：成员反复刷新活动详情页后收到多条相同训练提醒；短信失败后站内信和邮件各发送多条；后台任务重试把同一提醒标记为多个成功记录。

建议验证方式：模拟重复报名、重复保存提醒偏好、调度任务重试和渠道失败补偿，检查发送记录数量、去重键、用户实际收到的通知数量。

适合跟进的 worker：backend-dev、test-engineer。

### 7. 成员关闭提醒后不得被补偿发送打扰

通过标准：成员关闭训练提醒、关闭某一渠道或关闭所有提醒后，后续待发送提醒必须立即使用最新偏好，已排队但未发送的提醒应取消或失效。渠道失败补偿任务必须重新读取偏好状态。

失败示例：成员关闭邮件提醒后，短信失败补偿又发送邮件；关闭所有提醒后旧队列继续推送；页面显示关闭成功但后台仍把提醒标记为可发送。

建议验证方式：关闭提醒后触发原本排队的训练前提醒和失败补偿任务，检查队列状态、发送记录、页面确认文案和接口返回。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer。

### 8. 管理员群发不得误触达非目标成员

通过标准：管理员群发训练提醒前必须确认目标活动、目标训练、成员范围和渠道范围。部分渠道失败时，只能对原目标成员按原权限范围降级，不得扩大发送到整个跑团或其他活动成员。

失败示例：管理员给某活动报名成员群发集合提醒，邮件失败后系统改发给所有跑团成员；群发预览只显示人数不显示活动名称；失败重试没有保留原筛选条件。

建议验证方式：准备多个活动、多个报名状态和不同渠道偏好成员，执行群发预览、发送和失败重试，核对目标成员集合、中文二次确认和审计记录。

适合跟进的 worker：backend-dev、frontend-dev、security-reviewer、test-engineer。

### 9. 隐私字段不得出现在提醒正文和失败提示中

通过标准：通知正文、移动端弹窗、站内信、邮件正文、失败提示和内部审计摘要均不得暴露密码、完整手机号、完整邮箱、访问令牌、原始定位轨迹、其他成员训练详情或管理员内部备注。必要联系方式只能脱敏展示。

失败示例：异常提醒包含完整轨迹坐标数组；邮件失败提示展示完整收件地址；管理员群发失败列表把所有成员手机号明文导出；普通成员能看到其他成员关闭提醒的原因。

建议验证方式：安全扫描通知模板、接口响应、审计记录和导出内容，重点查找完整联系方式、令牌、原始轨迹和跨成员数据；用普通成员账号访问他人提醒偏好确认被拒绝。

适合跟进的 worker：security-reviewer、backend-dev、frontend-dev、test-engineer。

### 10. 移动端降级文案不能过长或不可操作

通过标准：移动端通知标题和正文必须为中文短句，标题说明训练或活动，正文说明时间、地点、失败原因或下一步动作之一。窄屏下不能遮挡“查看详情”“关闭提醒”“补充通知方式”等关键按钮。

失败示例：移动端标题显示 `training_reminder_failed`；正文长到看不到操作按钮；失败状态只用红色图标表达，没有文字；取消训练提醒仍展示原集合地点。

建议验证方式：使用三百七十五像素宽度检查训练前提醒、渠道失败、免打扰延后、取消训练和关闭提醒五类页面或通知样例，人工核对可读性。

适合跟进的 worker：frontend-dev、content-reviewer、test-engineer。

### 11. 失败状态必须可审计但不泄露内部堆栈

通过标准：渠道不可用、免打扰延后、重复去重、取消失效、权限拒绝和补偿发送都应保留内部审计记录。审计记录应包含训练或活动标识、成员标识脱敏、渠道类型、中文失败摘要、处理结果和时间，不应包含内部堆栈、访问令牌或完整联系方式。

失败示例：用户问为什么没有提醒时无法查到记录；审计日志只写英文异常码；日志包含邮件服务访问令牌；管理员界面直接展示数据库异常堆栈。

建议验证方式：分别触发六类失败和降级场景，检查审计记录字段、脱敏规则、中文摘要和管理员可见内容。

适合跟进的 worker：backend-dev、security-reviewer、test-engineer。

### 12. 异常提醒和复盘提醒降级不得生成医疗判断

通过标准：配速突变、距离异常、心率缺失、训练未完成或数据不足触发提醒时，降级文案只能提示复核数据、确认训练状态、注意恢复或联系团长确认，不得给出医疗诊断或确定性健康判断。

失败示例：心率缺失时邮件提醒写“身体风险很高”；配速偏慢时推送“你可能受伤”；数据不足时仍生成确定性训练建议并反复推送。

建议验证方式：复用异常提醒规则配置样例中的配速突变、距离异常、心率缺失、训练未完成和重复上传场景，核对各渠道和降级提示文案。

适合跟进的 worker：backend-dev、content-reviewer、test-engineer。

## 五、建议回归矩阵

1. 无手机号但有站内信：短信提醒不可用，降级为站内提醒，页面显示中文说明。
2. 无邮箱但有移动推送：邮件提醒不可用，改用移动推送或站内信，邮箱不明文展示。
3. 站内信写入失败且无其他渠道：提醒状态显示待补充通知方式，不标记为成功。
4. 免打扰覆盖训练前十分钟提醒：提醒按策略延后、提前或站内留存，不在免打扰内推送。
5. 成员取消报名：原训练前提醒取消，不再发送原集合通知。
6. 活动被管理员取消：必要时只发送取消说明，不发送“训练即将开始”。
7. 后台任务重试三次：同一成员同一训练只收到一条有效提醒。
8. 成员关闭全部提醒后触发补偿任务：补偿任务读取最新偏好并停止发送。
9. 管理员群发部分失败：重试只覆盖原目标成员，不扩大发送范围。
10. 普通成员尝试读取他人提醒偏好：请求被拒绝，不返回联系方式和偏好内容。
11. 异常复盘提醒渠道失败：降级文案保守，不出现医疗诊断。
12. 移动端窄屏展示：渠道失败和取消训练文案完整可读，按钮不被遮挡。

## 六、可复制到 kanban 评论的门禁摘要

训练提醒偏好通知失败降级门禁摘要：已补充中文验收清单，覆盖短信、站内信、邮件渠道缺失，免打扰冲突，训练取消后仍提醒，重复推送，成员关闭提醒，管理员群发误触达，隐私字段外泄，移动端文案过长，失败审计和异常复盘提醒保守表达。后续实现需保证通知失败不静默、降级不越权、免打扰和取消状态优先于补偿发送、同一业务提醒具备去重键，并且所有用户可见文案为中文且不泄露完整联系方式、令牌、原始轨迹或其他成员训练详情。
