# 校园跑团挑战赛排行榜功能规格

## 1. 背景与目标

1034 跑团管理系统已经具备成员管理、活动管理、报名、签到、公告和基础统计能力。README 与用户指南中已说明：当前可基于 `activity_participation_facts` 视图统计已签到活动的累计跑量，但还没有单独的排行页面或面向校园运营的挑战赛规则。

本规格提出“校园挑战赛排行榜”功能：在不依赖第三方 API、不引入 LLM/AI、不与活动瀑布流、跑步数据导入向导、成员里程徽章重复的前提下，把已有活动距离与签到数据组织成可展示、可运营、可测试的排行榜闭环。

核心目标：

1. 让成员看到自己在本周、本月或指定挑战周期内的跑步表现，形成参与动力。
2. 让团长按深圳技术大学校园社群风格运营“学院/班级/个人”挑战赛。
3. 让后端优先复用现有成员、活动、报名、签到与 `activity_participation_facts` 数据，降低开发量。
4. 让隐私和防作弊规则在首版就有明确边界，避免排行榜引发争议。

## 2. 现有能力与边界

### 2.1 可复用数据

| 来源 | 可用字段/能力 | 用途 |
|---|---|---|
| `members` | `id`、`name`、`role`、`running_years`、`pace`、`usual_distance_km`、`training_goal` | 成员展示、匿名化、最佳进步基线 |
| `activities` | `id`、`title`、`start_time`、`location`、`route`、`distance_km`、`pace_group` | 活动距离、活动日期、挑战周期归属 |
| `registrations` | `activity_id`、`member_id`、`status`、`created_at` | 报名状态辅助判断，不直接计入跑量 |
| `attendances` | `activity_id`、`member_id`、`status`、`signed_in_at`、`gps_checked` | 签到有效性、连续打卡、可信签到提示 |
| `activity_participation_facts` | `member_id`、`activity_date`、`participation_status`、`signed_in_at`、`gps_checked`、`activity_start_time` | 推荐作为排行榜聚合主数据源 |

### 2.2 不重复的设计边界

| 已有/规划模块 | 本规格避让方式 |
|---|---|
| 活动瀑布流 | 瀑布流解决“发现和报名活动”，排行榜解决“活动后的挑战成绩展示与运营闭环”。不新增活动卡片推荐规则。 |
| 跑步数据导入向导 | 导入向导解决“外部记录预检和字段映射”，排行榜只消费已进入系统且已签到的活动数据。 |
| 成员里程徽章 | 徽章是长期个人荣誉，排行榜是周期性、可重置的竞赛展示。首版不发徽章、不新增徽章规则。 |
| 数据统计页面 | 统计页偏运营分析，排行榜偏成员激励和公开展示。可复用统计卡片风格，但不替代统计页。 |

## 3. 挑战赛类型设计

### 3.1 个人周跑量榜

| 项目 | 内容 |
|---|---|
| 榜单 key | `weekly_distance_individual` |
| 运营名称 | 本周校园跑量榜 |
| 鼓励行为 | 鼓励成员每周至少参加一次有效活动并完成签到 |
| 排名口径 | 挑战周期内，成员所有 `participation_status = 'signed_in'` 活动的 `distance_km` 总和 |
| 周期 | 默认自然周，周一 00:00 到周日 23:59:59；也允许管理员选择自定义起止日期 |
| 并列规则 | 总跑量相同则按已签到活动场次降序，再按最近一次签到时间升序，再按 member_id 升序稳定排序 |
| 前端提示 | “仅统计已签到活动；未填写距离的活动按 0 公里计入。” |
| MVP 是否包含 | 是 |

### 3.2 学院/班级团队榜

| 项目 | 内容 |
|---|---|
| 榜单 key | `team_distance_group` |
| 运营名称 | 学院/班级团队接力榜 |
| 鼓励行为 | 鼓励同学院或同班级成员组队参与，形成校园集体荣誉感 |
| 排名口径 | 挑战周期内，同一团队成员有效跑量求和；展示团队人数、有效签到人次、人均跑量 |
| 团队来源 | 首版优先从成员资料扩展字段或管理员维护的轻量字段读取；如果当前数据模型没有学院/班级字段，MVP 可先使用“临时团队名称”配置，不强制新增表 |
| 并列规则 | 团队总跑量相同则按有效签到人次降序，再按人均跑量降序，再按团队名称升序 |
| 前端提示 | “团队榜统计公开团队总量，不展示成员手机号。” |
| MVP 是否包含 | 是，但允许先用静态团队字段或种子数据演示 |

### 3.3 连续打卡榜

| 项目 | 内容 |
|---|---|
| 榜单 key | `continuous_checkin_streak` |
| 运营名称 | 连续打卡坚持榜 |
| 鼓励行为 | 鼓励成员保持稳定参与习惯，而不是只冲单次跑量 |
| 排名口径 | 按活动日期计算连续签到天数或连续活动日次数；同一天多场活动只算 1 天 |
| 推荐首版口径 | 在挑战周期内，按 `activity_date` 去重后计算最长连续签到天数；没有每日活动时可显示“连续活动日”而非“连续自然日” |
| 并列规则 | 最长连续天数相同则按本周期有效签到活动场次降序，再按总跑量降序 |
| 前端提示 | “同一天多次签到只计 1 天连续记录。” |
| MVP 是否包含 | 是 |

### 3.4 最佳进步榜

| 项目 | 内容 |
|---|---|
| 榜单 key | `best_progress_distance` |
| 运营名称 | 最佳进步榜 |
| 鼓励行为 | 鼓励新手和中等活跃成员参与，避免榜单只被高跑量成员垄断 |
| 排名口径 | 本周期跑量相对基线周期跑量的增长值或增长率 |
| 基线周期 | 默认上一自然周；如果上一周为 0，采用最近 4 周平均跑量作为兜底；仍为 0 时展示“首次上榜”，不参与增长率排序，只按本周期跑量排序 |
| 并列规则 | 增长值相同则按增长率降序，再按本周期总跑量降序 |
| 前端提示 | “最佳进步榜不是绝对跑量榜，适合新成员查看成长。” |
| MVP 是否包含 | 是，但后端可先实现“本周比上周增长公里数”简化版 |

## 4. 前端展示规格

### 4.1 页面结构

建议新增一个轻量页面或统计页内入口：

- 页面标题：`校园挑战赛排行榜`
- 副标题：`深技大跑团 · 本周挑战`
- 顶部筛选区：挑战类型、周期、团队维度、只看我的排名
- 榜单摘要卡：参与人数、有效签到次数、总跑量、最近更新时间
- 排行列表：前三名突出展示，其余以表格或列表展示
- 规则说明抽屉：说明统计口径、隐私规则和防作弊提示
- 空状态：暂无有效签到数据时，引导用户查看近期活动而不是显示空白

视觉建议复用现有深技大活动瀑布流规范：深色背景、科技蓝 `#38bdf8`、活力绿 `#22c55e`、圆角卡片、清晰焦点态。

### 4.2 通用字段

| 字段 | 类型 | 示例 | 说明 |
|---|---|---|---|
| `leaderboard_key` | string | `weekly_distance_individual` | 榜单类型 |
| `title` | string | `本周校园跑量榜` | 前端标题 |
| `period_label` | string | `2026-06-01 至 2026-06-07` | 周期展示 |
| `updated_at` | string | `2026-06-07T22:00:00+08:00` | 最近计算时间 |
| `rank` | number | `1` | 当前排名 |
| `display_name` | string | `张同学` | 脱敏展示名 |

| `team_name` | string/null | `计算机学院` | 团队榜使用 |

### 4.3 个人周跑量榜展示字段

- 排名
- 昵称/脱敏姓名
- 本周累计公里数
- 已签到活动数
- 最近一次签到日期
- 是否 GPS 签到占比高（可显示“可信签到 3/4”）
- “我的排名”固定浮条：未上榜时显示“本周还没有有效签到”

### 4.4 学院/班级团队榜展示字段

- 排名
- 团队名称
- 团队总公里数
- 有效参与人数
- 有效签到人次
- 人均公里数
- 团队本周亮点文案：例如“计算机学院本周新增 12 次签到”

### 4.5 连续打卡榜展示字段

- 排名
- 脱敏姓名
- 最长连续打卡天数/连续活动日
- 本周期签到活动数
- 连续区间：例如 `06-01 至 06-05`
- 中断提示：仅当前用户可见，如“昨天未签到，连续记录已重置”

### 4.6 最佳进步榜展示字段

- 排名
- 脱敏姓名
- 本周期跑量
- 基线周期跑量
- 增长公里数
- 增长率
- 新手友好标记：基线不足时显示“首次上榜”，不夸大增长率

## 5. 后端数据聚合规格

### 5.1 推荐 API

新增只读接口，首版不需要新增写接口：

```http
GET /api/v1/leaderboards/challenges?type=weekly_distance_individual&period_start=2026-06-01&period_end=2026-06-07&limit=20
```

可选参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `type` | string | 是 | 榜单类型 key |
| `period_start` | date | 否 | 挑战开始日期，默认本周一 |
| `period_end` | date | 否 | 挑战结束日期，默认本周日 |
| `team_dimension` | string | 否 | `college` 或 `class`，团队榜使用 |
| `limit` | integer | 否 | 默认 20，最大 100 |
| `include_me` | boolean | 否 | 是否返回当前登录用户排名摘要 |

返回结构示例：

### 5.2 个人周跑量 SQL 口径

首版可基于现有视图与活动表聚合：

```sql
SELECT
  m.id AS member_id,
  m.name,
  COUNT(DISTINCT f.activity_id) AS signed_in_activities,
  COALESCE(SUM(a.distance_km), 0) AS total_distance_km,
  MAX(f.signed_in_at) AS last_signed_in_at,
  SUM(CASE WHEN f.gps_checked THEN 1 ELSE 0 END) AS gps_signed_in_count
FROM activity_participation_facts f
JOIN members m ON m.id = f.member_id
JOIN activities a ON a.id = f.activity_id
WHERE f.participation_status = 'signed_in'
  AND DATE(f.activity_date) BETWEEN :period_start AND :period_end
GROUP BY m.id, m.name
ORDER BY total_distance_km DESC,
         signed_in_activities DESC,
         last_signed_in_at ASC,
         m.id ASC
LIMIT :limit;
```

### 5.3 团队榜聚合口径

如果已有成员字段可表示学院/班级：

```sql
SELECT
  COALESCE(m.college, '未填写学院') AS team_name,
  COUNT(DISTINCT m.id) AS active_members,
  COUNT(DISTINCT f.activity_id || ':' || f.member_id) AS signed_in_records,
  COALESCE(SUM(a.distance_km), 0) AS total_distance_km,
  ROUND(COALESCE(SUM(a.distance_km), 0) * 1.0 / NULLIF(COUNT(DISTINCT m.id), 0), 2) AS avg_distance_km
FROM activity_participation_facts f
JOIN members m ON m.id = f.member_id
JOIN activities a ON a.id = f.activity_id
WHERE f.participation_status = 'signed_in'
  AND DATE(f.activity_date) BETWEEN :period_start AND :period_end
GROUP BY team_name
ORDER BY total_distance_km DESC,
         signed_in_records DESC,
         avg_distance_km DESC,
         team_name ASC;
```

如果当前模型没有 `college` 或 `class_name` 字段，MVP 可采用两种降级方案之一：

1. 后端返回个人榜，前端隐藏团队榜入口并提示“团队榜待完善成员资料后开放”。
2. 使用管理员维护的本地演示映射或种子数据，不写入正式业务表；验收时明确这是演示模式。

### 5.4 连续打卡聚合口径

计算步骤：

1. 查询周期内每个成员所有有效签到活动日期。
2. 对同一成员同一天多次签到去重。
3. 按日期升序扫描，计算最长连续自然日数量。
4. 如果活动不是每日举办，可在文案中命名为“连续活动日”，避免误导。
5. 返回最长连续段的开始日期、结束日期和长度。

边界：跨月、跨年按日期连续判断；补签按活动日期计入，而不是按补签操作时间计入。

### 5.5 最佳进步聚合口径

计算步骤：

1. 统计当前周期每个成员 `current_distance_km`。
2. 统计基线周期每个成员 `baseline_distance_km`，默认上一自然周。
3. 计算 `progress_distance_km = current_distance_km - baseline_distance_km`。
4. 当 `baseline_distance_km > 0` 时计算 `progress_rate = progress_distance_km / baseline_distance_km`。
5. 当基线为 0 时不计算增长率，显示 `first_time_ranked = true`。
6. 只展示 `current_distance_km > 0` 的成员，避免未参与成员占榜。

## 6. 隐私与防作弊注意点

### 6.1 隐私规则

1. 公开榜单默认不展示手机号、完整个人资料、训练目标等敏感或半敏感信息。
2. 普通成员看到其他人时使用脱敏名，例如 `张同学`、`李*` 或社团昵称；管理员和团长可在管理视图查看完整姓名。
3. “我的排名”可以展示完整个人数据，但只对本人可见。
4. 团队榜展示团队总量和人均值，不默认展开团队成员明细。
5. 如果团队人数小于 3 人，建议隐藏人均数据或合并为“其他团队”，避免间接识别个人跑量。
6. API 返回中不要包含手机号；如确需调试，测试数据也应脱敏。

### 6.2 防作弊规则

1. 只有 `participation_status = 'signed_in'` 的活动计入榜单；仅报名、取消报名、缺席都不计入。
2. 活动距离来自活动表 `distance_km`，不是用户自行填写，避免个人随意上报距离。
3. 同一成员同一活动只计入一次，依赖签到表和报名表的唯一约束。
4. 同一天多场活动可以计入个人跑量，但连续打卡只计 1 天。
5. `gps_checked = false` 的签到可以计入，但在榜单中显示“未定位签到”提示；如果管理员开启严格模式，可排除未 GPS 校验记录。
6. 对异常高跑量设置运营提示阈值，例如单周超过 100 km 或单日超过 30 km 时，在管理端标记“需复核”，但不自动删除成绩。
7. 活动距离为空或负数时：空值按 0 公里，负数应在活动创建或数据导入阶段被校验拒绝。
8. 排行榜计算应可重复，排序必须有稳定兜底字段，避免同分成员刷新后顺序随机变化。

## 7. MVP 范围

首版建议实现以下内容：

1. 一个只读排行榜 API：支持 4 种 `type`，默认按本周周期查询。
2. 一个前端排行榜页面或统计页入口：展示挑战类型切换、周期标题、摘要卡、前 20 名榜单和规则说明。
3. 个人周跑量榜：完整实现。
4. 连续打卡榜：完整实现“连续活动日/自然日”计算。
5. 最佳进步榜：实现“本周比上周增长公里数”。
6. 团队榜：如果成员模型已有学院/班级字段则实现；否则提供演示模式或隐藏入口，并在规则说明中标注原因。
7. 隐私脱敏：普通成员不看到手机号和完整个人资料。
8. 防作弊提示：至少展示“仅统计已签到活动”和“同活动只计一次”。
9. 测试覆盖：后端聚合排序、空数据、并列排序、脱敏规则；前端切换榜单和空态。

## 8. 非目标

首版不做以下内容：

1. 不接入微信、Keep、Strava、Garmin 等第三方 API。
2. 不做 AI 推荐、LLM 总结或自动生成运营话术。
3. 不新增复杂赛季系统、奖品发放系统或积分商城。
4. 不实现用户自行上传跑步轨迹；跑量只来自系统活动距离与有效签到。
5. 不改造活动瀑布流，不新增活动推荐算法。
6. 不把排行榜结果写入成员徽章体系；徽章可后续独立消费排行榜结果。
7. 不强制新增数据库表；若团队榜缺少学院/班级字段，先降级处理。
8. 不允许普通成员修改自己的榜单成绩。

## 10. 验收标准

### 10.1 产品验收

1. 页面能清楚说明 4 类挑战赛：个人周跑量、学院/班级团队榜、连续打卡、最佳进步。
2. 每类榜单都有明确统计口径、并列排序规则和边界提示。
3. 至少能展示 3 条样例排行榜数据；最终实现时可用测试夹具替代真实数据。
4. 普通成员视角不展示手机号和完整敏感资料。
5. 空数据时展示中文空态，不出现空白页面或英文调试信息。
6. 榜单规则说明能解释“为什么某次报名没有计入跑量”。

### 10.2 后端验收

1. `GET /api/v1/leaderboards/challenges` 在默认参数下返回本周个人跑量榜。
2. 只统计 `participation_status = 'signed_in'` 的记录。
3. 活动 `distance_km` 为空时按 0 处理。
4. 同一活动同一成员只计一次。
5. 并列排序稳定，至少包含总跑量、签到场次、最近签到时间、成员 ID 或团队名兜底。
6. `limit` 有上限，不能一次返回无限数据。
7. 未登录或权限不足时遵循现有鉴权规则；普通成员不能看到其他成员敏感字段。

### 10.3 前端验收

1. 可在 4 类榜单之间切换，切换后标题、摘要卡、列表字段同步变化。
2. 榜单加载中、空数据、接口错误、筛选无结果均有中文状态。
3. “我的排名”在当前用户存在成绩时高亮；无成绩时显示引导文案。
4. 页面风格复用深技大深色科技风，不破坏现有活动瀑布流和统计页面。
5. 移动端宽度下榜单字段不溢出，关键字段优先展示。

### 10.4 测试验收

1. 后端测试覆盖个人跑量榜排序和空距离处理。
2. 后端测试覆盖连续打卡同一天去重和跨日期连续判断。
3. 后端测试覆盖最佳进步榜基线为 0 的展示逻辑。
4. 后端测试覆盖团队榜团队人数、人均值和并列排序。
5. 前端测试或静态检查覆盖榜单切换、空态和错误态。
6. 隐私测试确认 API 返回不包含手机号字段。
