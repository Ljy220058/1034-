# 跑团功能路线图与任务入口文档

## 概述

本文档把 1034 跑团管理系统当前已完成和正在推进的功能方向整理成可派发的后续任务入口。

## 会员数据

## 概述

会员数据方向负责把成员资料、活动报名、活动签到和跑量统计沉淀成可分析的数据基础。
当前项目已经有成员、活动、报名、签到接口。
项目也有 `activity_participation_facts` 数据库视图，可用于跑量排行和参与分析。

## 参数说明

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| member_id | integer | 是 | 成员 ID，用于关联报名、签到和跑量统计 |
| activity_id | integer | 是 | 活动 ID，用于关联活动距离、开始时间和签到事实 |
| participation_status | string | 是 | 参与状态，建议区分 `registered`、`cancelled`、`signed_in`、`absent` |
| as_of_date | date | 否 | 统计日期，用于留存分层和近期活跃窗口 |
| window_days | integer | 否 | 统计窗口天数，例如 30 天或 90 天 |


## 后续可执行入口

| 任务入口 | 优先级 | 依赖关系 | 建议 worker | 验收口径 |
|----------|--------|----------|-------------|----------|
| 补充成员跑量排行只读 API | P0 | 依赖 `activity_participation_facts` 视图和活动距离字段 | backend-dev | `GET` 接口返回成员 ID、姓名、签到场次、总公里数；SQL 使用参数化查询；补充 API 文档和 curl 验证结果 |
| 建立 30/90 天留存分层查询 | P1 | 依赖成员创建时间、活动开始时间、报名状态和签到状态 | data-analyst、backend-dev | 给出高参与、稳定参与、偶尔参与、流失风险、新成员未激活的稳定规则；示例数据可复算 |
| 成员资料完整度检查 | P1 | 依赖成员表中的跑龄、配速、常跑距离和训练目标 | backend-dev、docs-writer | 输出缺失字段清单和修复建议；不泄露手机号等敏感信息 |
| 数据异常签到清单 | P2 | 依赖报名表和签到表关联 | data-analyst | 找出有签到但无报名、活动未开始却已签到、重复事实等异常；返回原因说明 |

## 注意事项

- 跑量排行只统计已签到活动，已报名但未签到不计入总公里数。
- 活动距离为空时应按 `0` 或排除处理，具体口径必须在接口返回中说明。
- 手机号属于敏感字段，运营诊断输出不应直接展示完整手机号。
- 留存分层应以活动开始时间为统计时间轴，避免补录签到时间改变历史归因。

| 任务入口 | 优先级 | 依赖关系 | 建议 worker | 验收口径 |
|----------|--------|----------|-------------|----------|
| 跑步数据导入字段规范 | P1 | 依赖成员、活动、报名、签到表字段 | docs-writer、data-analyst | 输出字段映射表，说明哪些字段写成员、哪些字段写活动或签到；无歧义字段名 |
| CSV 导入预检接口 | P1 | 依赖字段规范和工作区路径校验 | backend-dev | dry run 不写库；返回有效行、无效行、错误原因和报告路径；错误信息为中文 |
| 导入向导前端页面 | P2 | 依赖预检接口和报告格式 | frontend-dev | 支持上传或粘贴数据、显示校验结果、禁止未确认时写入 |
| 导入回滚说明 | P2 | 依赖导入批次 ID 或幂等键 | docs-writer、backend-dev | 文档说明如何按批次查看、撤回或重新导入；不要求自动回滚已上线数据 |

## 注意事项

- 第一版导入建议先做 dry run，确认字段映射和错误提示稳定后再允许写入数据库。
- 导入报告必须写清楚失败行号和失败原因，不能只写“格式错误”。
- 如果导入成员手机号，应脱敏展示，避免在报告中保留完整手机号。
- 任务元数据导入和跑步业务数据导入是两类入口，文档和接口命名应区分。

## 给后续 kanban 创意生成器的复用方式

## 概述

后续 kanban 创意生成器可以把本文档当作任务种子库。
每次生成任务时，先选择一个分组，再从该分组的“后续可执行入口”中挑选一项，补齐标题、正文、负责人、工作区和验收口径。

## 快速开始

生成器读取入口：

```bash
cd /root/autodl-tmp/projects/hermes-swarm-lab
sed -n '/## 任务入口总览/,$p' docs/跑团功能路线图与任务入口.md
```

推荐生成规则：

```text
1. 优先派发 P0，再派发 P1，最后派发 P2。
2. 同一批任务不要同时派发相同依赖的多个下游任务。
3. 代码实现任务交给 backend-dev 或 frontend-dev。
4. 诊断、指标和 SQL 口径任务交给 data-analyst 或 backend-dev。
5. 文档、验收清单和交接说明任务交给 docs-writer 或 reviewer。
6. 每张卡必须包含工作区：dir:/root/autodl-tmp/projects/hermes-swarm-lab。
```

## 参数说明

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| group | string | 是 | 分组名称：会员数据、活动展示、导入向导、运营诊断、看板协作 |
| priority | string | 是 | 优先级：P0、P1、P2 |
| assignee | string | 是 | 建议 worker，例如 `backend-dev`、`frontend-dev`、`docs-writer` |
| workspace_kind | string | 是 | 固定为 `dir` |
| workspace_path | string | 是 | 固定为 `/root/autodl-tmp/projects/hermes-swarm-lab` |
| acceptance | array[string] | 是 | 验收口径，必须能被人工或测试复核 |

## 返回示例

```json
{
  "title": "补充成员跑量排行只读 API",
  "assignee": "backend-dev",
  "workspace_kind": "dir",

}
```

## 注意事项

- 生成器不要把本文档中的示例 JSON 当作真实接口返回承诺。
- 如果任务涉及接口文档，docs-writer 必须先用代码和 curl 验证再写文档。
- 如果任务涉及业务代码修改，完成后需要 reviewer 复核变更文件、测试命令和关键输出。
- 如果任务只输出文档，完成时应在 kanban 评论和 summary 中写明文档绝对路径。
