# 看板任务运行时限与失败重试策略

本文档给调度器、worker 和人工审核者一套可复用的默认配置与判断口径，避免任务无限运行、无限失败重试或占住空闲 worker。

配置示例：`deploy/kanban-task-runtime.example.yml`
本地验证脚本：`scripts/validate-kanban-runtime-config.sh`

## 新增的中文自助恢复提示文案

当 worker 遇到阻塞、依赖未完成或临时失败时，可以优先向执行者输出以下中文提示，帮助快速判断下一步该查什么：

1. `当前任务已进入阻塞态，请先检查上游依赖、权限和输入是否齐备。`
2. `检测到测试或校验失败，请优先查看最近一次报错堆栈和失败命令。`
3. `如果是上下文缺失，请补充最小必要信息后继续执行，不要重复空跑。`
4. `若问题看起来是临时抖动，可先重试一次；若结果稳定失败，请转向配置或依赖排查。`

这些提示应当尽量放在任务说明、错误提示或执行入口旁边，避免执行者在没有上下文时反复猜测。

## 推荐默认值

- `max_runtime_seconds: 3600`：单个任务默认最多运行 1 小时。
- `max_retries: 2`：同一任务最多自动重试 2 次。
- `requeue_strategy: retry_transient`：默认只对临时、幂等、可恢复错误重新入队。

这些默认值的目标是：

1. 普通文档、配置、轻量代码任务不会长期占用 worker。
2. 临时失败有自动恢复机会。
3. 确定性失败会尽快转入人工判断，避免重复消耗资源。

## 调度器何时应重新入队

满足以下条件时，可以把任务重新置为 `ready`：

- 任务未产生不可回滚副作用。
- 失败看起来是临时问题，例如资源抖动、进程被临时终止、可幂等重跑的命令超时。
- 当前连续失败次数小于 `max_retries`。
- 超时任务最近仍有 heartbeat，说明 worker 曾持续推进，只是需要更小任务粒度或更长 `max_runtime_seconds`。

建议中文提示：

`任务失败但看起来是临时问题，已按 max_retries 策略重新入队。`

## 调度器何时应阻断

满足以下任一条件时，应停止自动重试并进入 `blocked` 或人工复核状态：

- 缺少密钥、权限、人工审批或明确需求选择。
- 同一校验、构建或启动步骤确定性失败，继续重试不会改变结果。
- 任务已经执行删除、覆盖、发布、迁移等不可幂等动作，自动重试可能扩大影响。
- `retry_counter >= max_retries`。

建议中文提示：

`任务已达到最大重试次数，为避免阻塞 worker 和浪费资源，已停止自动重试并等待人工处理。`

## 每类任务的覆盖建议

| 任务类型 | max_runtime_seconds | max_retries | requeue_strategy |
| --- | ---: | ---: | --- |
| 短文档/配置任务 | 900 | 1 | retry_transient |
| 构建/部署任务 | 1800 | 2 | retry_transient |
| 长数据处理任务 | 7200 | 1 | retry_transient，必须定期 heartbeat |
| 凭据/审批/需求选择任务 | 600 | 0 | block_permanent |
| 破坏性发布/删除任务 | 600 | 0 | never_retry_destructive |

## 本地验证

该验证不依赖外部网络，只检查示例文件是否包含必需字段、默认值、重新入队策略和中文错误提示：

```bash
./scripts/validate-kanban-runtime-config.sh
```

预期输出包含：

```text
OK: kanban task runtime/retry config example is valid
```

## 给 worker 的执行建议

- 任务预计超过 1 小时时，至少每小时发送一次 heartbeat，并在备注里写清当前进度。
- 失败前先判断是否幂等；不幂等任务失败后不要自动重试。
- 需要人工输入时，不要用重试代替提问；直接转人工判断。
- 自动重试只解决临时错误，不解决配置错误、权限错误和需求歧义。
