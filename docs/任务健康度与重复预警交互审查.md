# 代码审查报告
## 严重（必须修）
- [backend/routes/members.py:37] 非管理员创建成员时，直接写入固定明文密码 `secret123`，且未要求用户提供初始密码；这会导致所有通过该接口创建的账号共享同一弱密码，属于高危账号接管风险 → 建议：改为必填初始密码或使用一次性重置链接/随机临时口令，并立即强制首次登录改密。
- [backend/repository.py:283-286] `update_member` 通过 `data` 动态拼接 `SET` 字段名：`assignments = ', '.join(f'{key} = ?' for key in data)`，虽然值参数化了，但字段名完全来自请求体，`model_dump(exclude_unset=True)` 无法保证未来字段扩展时不会把非列名拼入 SQL；这是典型的动态 SQL 拼接面，后续极易演变为注入/越权更新 → 建议：改成白名单映射，只允许预定义列参与更新，并显式构造更新语句。
- [backend/routes/auth.py:29-31,61-63] 密码使用 SHA-256 直接哈希后入库/校验，没有加盐、没有慢哈希，且种子数据中还存在可见弱哈希占位，离线撞库成本极低 → 建议：改用 `bcrypt`/`argon2` 等专用密码哈希，并加入现有用户迁移策略。
- [backend/routes/members.py:37-38] 创建成员时由服务端硬编码 `UserRegister(password='secret123', ...)`，若该接口被管理员或领导误用，会把新成员密码固定为同一个值，且响应直接返回完整公开成员数据，后续很容易引发未授权登录与账号滥用 → 建议：要求前端传入初始密码，或返回一次性初始化令牌而不是固定密码。

## 中等（应该修）
- [backend/routes/tasks.py:110,195] `_validated_workspace_path` 在批量导入和单条创建中都接受请求体中的 `workspace_path`，然后把它传入 `validate_workspace_access_path`；该校验只做“禁止越界/隐藏目录”，并不校验业务上是否允许跨工作区写入，等于让任意有 leader/admin 权限的人把任务写到任意合法工作区路径 → 建议：增加工作区白名单/归属校验，至少限制到当前租户或当前项目根目录。
- [backend/routes/workspaces.py:30-38] `_safe_workspace_path` 允许任意绝对/展开路径，只要是目录且不含 `..` 或隐藏段就通过；这会让高权限用户枚举和读取服务器上任意非隐藏目录的任务/状态汇总，扩大了文件系统暴露面 → 建议：把可访问范围收窄到预定义 workspace 根目录下，或仅允许当前项目 workspace。
- [backend/routes/checkins.py:111-115] 自助签到接口接受路径参数 `activity_id`，但请求体里还可携带 `member_id`；虽然最终对非管理员做了“当前用户必须等于 member_id”的校验，但接口仍允许客户端伪造任意 member_id 来探测他人签到/报名状态差异，导致可枚举性增强 → 建议：对普通成员忽略/禁止提交 `member_id`，直接从当前登录用户推导。
- [backend/routes/auth.py:57-63] 登录查询按手机号返回整行 `SELECT * FROM members`，再对密码哈希进行比较；如果数据库中存在任意可控脏数据或未来新增敏感列，会被无差别拉取到内存中，扩大泄露面 → 建议：只选择必要字段（`id`, `role`, `password_hash`）以缩小暴露面。
- [backend/settings.py:125-150] `validate_workspace_access_path` 对绝对路径先 `resolve()` 再做相对性判断；如果调用方传入的路径不存在，`resolve()` 会抛出异常或把校验语义绑定到文件系统当前状态，导致错误处理不稳定；同时仅靠 `..` 和隐藏段过滤不足以阻止符号链接穿越 → 建议：先做纯路径语义校验，再对存在性单独检查，并显式拒绝符号链接链路。

## 建议（可以修）
- [backend/app.py:78-92] 全局 `Exception` handler 会把所有未预期错误统一改写成 JSON 响应，虽然避免泄露堆栈，但也会掩盖服务端故障分类，排障时只能靠日志 → 建议：保留统一响应的同时补充结构化错误日志，至少记录请求路径和异常类型。
- [backend/routes/tasks.py:72-75] `_normalize_batch_item` 用裸 `except Exception` 包裹 Pydantic 校验，异常粒度过宽，后续如果内部代码出现其他异常也会被误判成“数据校验失败” → 建议：只捕获 `ValidationError`，其他异常继续抛出。
- [backend/repository.py:407-423,441-446] `create_registration` / `create_attendance` 在重建记录时把 `created_at`/`signed_in_at` 直接重写，语义上更像“恢复/更新”而不是“创建”；如果审计依赖创建时间，这会让历史轨迹失真 → 建议：保留原始时间字段，新增单独的 `updated_at` 或状态变更时间。
- [backend/routes/members.py:46-67] 普通用户可读取/修改自己的成员资料，但 `patch_member` 允许更新字段集合较大，未来若模型增加敏感字段，默认会自动暴露为可修改项 → 建议：为可修改字段建立显式白名单，而不是直接透传模型。
- [backend/routes/checkins.py:209-225] 删除签到接口实际上只会返回 405，不是真正删除；当前实现依赖调用者自己理解“用撤销接口”这一约定，容易让前端/自动化脚本误判为删除失败 → 建议：在 API 文档和返回体里显式标注为“禁止删除，仅允许撤销”，或直接不暴露 DELETE 路由。
