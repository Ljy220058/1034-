# 签到补签撤销流程代码审查报告

## 审查范围
- 后端：`backend/routes/checkins.py`、`backend/attendance.py`、`backend/repository.py`、`backend/routes/activities.py`、`backend/models.py`、数据库 schema。
- 前端：`frontend/api.js`、`frontend/app.js`、`frontend/index.html` 中签到/出勤相关能力检索。
- 测试：`tests/test_checkin.py`。
- 验证命令：`python -m pytest tests/test_checkin.py -q`，结果 5 失败。

## 现有能力
- 已有签到记录列表、创建/更新、详情、删除接口：`GET/POST /api/v1/activities/{activity_id}/checkins`、`GET/DELETE /api/v1/activities/{activity_id}/checkins/{attendance_id}`。
- 普通成员只能给自己签到，管理员/领队可给任意成员创建签到记录。
- 创建签到前检查活动、成员存在，并要求报名状态为 `registered`。
- 数据库对 `(activity_id, member_id)` 建唯一约束，避免同一成员同活动重复插入多条出勤记录。

## 严重（必须修）
- [backend/routes/checkins.py:87] `get_attendance(attendance_id)` 调到的是 `backend/repository.py:463` 的同名函数，该函数签名是 `get_attendance(activity_id, member_id)`，导致详情接口运行时 `TypeError`，`DELETE` 路径同样会在 `backend/routes/checkins.py:106` 触发。实际验证：`tests/test_checkin.py::test_checkin_list_detail_delete_permissions_and_missing_cases` 失败。→ 建议：消除同名导入/定义冲突，明确从 `backend.attendance` 引入按 attendance_id 查询的函数，例如 `from ..attendance import get_attendance as get_attendance_by_id`，并在路由中调用 `get_attendance_by_id(attendance_id)`；或把 repository 里的二元查询重命名为 `get_attendance_by_activity_member(activity_id, member_id)`。

- [backend/routes/checkins.py:93] “撤销签到”当前实现为 `DELETE` 硬删除出勤记录，数据库也没有 `revoked_at`、`revoked_by`、`revoke_reason` 或审计表。管理员/领队一旦误删或恶意删除，系统无法追溯谁在什么时间撤销、撤销原因是什么，也无法区分“从未签到”和“签到后被撤销”。→ 建议：改为软撤销，新增状态如 `revoked` 或新增 `attendance_events` 审计表；接口改为 `POST /checkins/{attendance_id}/revoke`，请求体强制包含 `reason`，写入 `revoked_by=current_user.id`、`revoked_at=now()`，列表/详情返回撤销状态和审计信息。

- [backend/attendance.py:113] 重复签到会无条件 `UPDATE attendances SET status='signed_in', signed_in_at=?, gps_checked=?`；如果请求没有传 `checked_in_at`，`backend/attendance.py:95` 会使用当前时间覆盖原签到时间。普通成员可以通过重复提交刷新自己的签到时间和 GPS 状态，管理员补签也会覆盖既有真实签到时间，造成出勤数据被篡改。实际验证：`tests/test_checkin.py::test_checkin_create_contract_and_idempotency` 失败，重复签到时间被改写。→ 建议：把“普通签到”和“管理员补签/更正”拆开；普通成员已有 `signed_in` 记录时返回 409 或原记录，不允许覆盖时间；管理员更正需走单独接口并记录 `corrected_by`、`corrected_at`、`correction_reason`、原值和新值。

## 中等（应该修）
- [backend/routes/checkins.py:59] 管理员/领队补签复用普通签到接口，允许对任意 `member_id` 写入任意 `checked_in_at`，但没有补签原因、操作者、来源类型、时间窗口限制。该能力可落地但风险不可控：管理员可以为任意报名成员补历史任意时间，事后无法解释。→ 建议：新增专用补签接口 `POST /api/v1/activities/{activity_id}/checkins/backfill`，只允许 `admin/leader`，请求体示例：`{member_id, checked_in_at, reason}`；校验 `reason` 非空、`checked_in_at <= now`、可选限制不能早于活动开始前 N 小时，并落库 `created_by`/`source='manual_backfill'`。

- [backend/attendance.py:103] 出勤创建强制要求已有 `registrations.status='registered'`，这能保护普通签到，但没有管理员补签未报名成员的业务分支。如果实际运营需要“补报名+补签”或现场临时成员补签，当前只能先调用报名接口，再调用签到接口，而且两个操作不是事务，失败会留下半完成状态。→ 建议：明确产品规则：若允许管理员给未报名成员补签，则专用补签接口应在同一数据库事务内创建/恢复报名并写签到；若不允许，则错误信息应明确返回 409 `member must be registered before backfill`，并在前端引导先报名。

- [backend/routes/checkins.py:47] `POST /checkins` 对普通成员开放时接受客户端传入的 `checked_in_at`，普通用户可以提交过去或未来时间实现“补签/预签到”。这把管理员补签能力泄露给了普通成员。→ 建议：普通成员签到时忽略请求体中的 `checked_in_at`，统一使用服务端时间；只有 `admin/leader` 的补签接口允许传 `checked_in_at`，并校验不得晚于当前时间。

- [frontend/api.js:1] 前端 API 客户端中未提供 `listActivityCheckins`、`createCheckin`、`deleteCheckin/revokeCheckin` 等封装；全仓检索 `checkins|attendance|signed_in|gps_checked|补签|撤销|签到|出勤` 在前端 JS/HTML 未命中。补签与撤销没有可操作入口，也无法展示撤销审计信息。→ 建议：在 `frontend/api.js` 增加签到 API 方法，在活动详情页增加“补签”“撤销签到”入口；补签表单包含成员、签到时间、原因，撤销二次确认必须填写原因。

- [tests/test_checkin.py:119] 测试只覆盖领队删除成功，没有覆盖“硬删除后审计不可追踪”“管理员补签必须填写原因”“普通成员不能传任意 `checked_in_at`”“重复签到不得覆盖原时间”等关键风险。当前测试还与实际响应结构/状态码不一致，5 个用例失败，无法作为回归门禁。→ 建议：重写签到测试矩阵：普通签到幂等不覆盖、普通成员传 `checked_in_at` 被忽略、管理员补签写入 audit 字段、撤销软删除保留记录、未报名补签规则、非管理员撤销 403。

## 建议（可以修）
- [backend/models.py:110] `AttendanceCreate.activity_id` 允许出现在请求体，随后 `backend/routes/checkins.py:24` 静默改成 path 中的 `activity_id`。静默纠正会掩盖客户端调用错误，也让审计日志难以判断原始请求是否异常。→ 建议：请求体移除 `activity_id`，只信任 path；若保留该字段，发现不一致时返回 422，提示客户端修正。

- [backend/attendance.py:128] 出勤列表按 `id ASC` 排序，而 `backend/repository.py:523` 的同名列表函数按 `signed_in_at DESC, id DESC` 排序；同一领域存在两套排序语义，后续页面和测试容易出现不一致。→ 建议：只保留一套 attendance repository，并统一列表排序为 `signed_in_at DESC, id DESC` 或产品指定顺序。

- [backend/database.py:54] `attendances` 表只有当前状态，没有事件历史；补签、更正、撤销都属于审计敏感操作，仅靠当前行无法满足后续追责。→ 建议：新增 `attendance_events(id, attendance_id, action, actor_id, reason, before_json, after_json, created_at)`，所有手工补签/更正/撤销均追加事件。

## 权限风险汇总
- 普通成员可通过 `checked_in_at` 自行补历史/未来签到，缺少服务端时间约束。
- 管理员/领队补签与普通签到共用接口，缺少补签原因、操作者和来源标识。
- 撤销为硬删除，管理员/领队权限过大且无审计。

## 数据一致性风险汇总
- 重复签到覆盖原 `signed_in_at` 和 `gps_checked`，破坏签到原始事实。
- 详情/删除接口因同名函数冲突不可用，撤销流程无法稳定执行。
- 未报名补签需要跨报名和签到两张表，但当前没有事务化的业务入口。
- 同一领域在 `backend/attendance.py` 与 `backend/repository.py` 中存在重复/冲突函数，容易继续产生调用错误。

## 建议的最小实现步骤
1. 修复 `get_attendance` 命名冲突，保证详情和撤销接口不再 500。
2. 将普通签到改为服务端时间；普通成员请求体中的 `checked_in_at` 不生效或直接 422。
3. 增加专用管理员补签接口，强制 `member_id + checked_in_at + reason`，写入 `source/manual_backfill`、`created_by`、`reason`。
4. 将删除改为软撤销接口，写入 `revoked_by`、`revoked_at`、`revoke_reason`，保留原签到记录。
5. 增加 `attendance_events` 审计表，记录补签、更正、撤销的 before/after。
6. 前端增加补签表单、撤销确认弹窗、出勤列表状态展示和审计信息展示。
7. 补齐测试矩阵并让 `python -m pytest tests/test_checkin.py -q` 通过。

## 验收用例
- 普通成员签到：不传时间，后端使用服务端时间创建 `signed_in`；重复提交返回原记录或 409，不改写原 `signed_in_at`。
- 普通成员伪造时间：提交 `checked_in_at='2030-01-01T00:00:00Z'` 不会写入该时间，或返回 422。
- 管理员补签：`admin/leader` 调补签接口，传 `member_id`、历史 `checked_in_at`、`reason`，返回记录含 `source='manual_backfill'`、`created_by`、`reason`，审计表有事件。
- 管理员补签未报名成员：按产品规则要么同事务创建报名+签到，要么明确 409 并不写任何签到记录。
- 撤销签到：`admin/leader` 填写原因撤销后，出勤详情仍可查询，状态为 `revoked`，包含 `revoked_by`、`revoked_at`、`revoke_reason`；列表可筛选/显示撤销状态。
- 非管理员撤销：普通成员调用撤销接口返回 403，原记录不变。
- 回归测试：`python -m pytest tests/test_checkin.py -q` 全部通过，并新增补签/撤销审计测试。
