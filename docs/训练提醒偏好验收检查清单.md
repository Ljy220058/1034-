# 训练提醒偏好验收检查清单

## 一、适用范围

本文档用于验收“训练提醒偏好”功能的后续实现，帮助产品、前端、后端、测试和安全相关跟进人员在开发前统一通知时机、中文文案、隐私边界和降级策略。

训练提醒偏好指成员是否接收训练相关提醒、提前多久提醒、是否启用免打扰时段、通过哪些渠道接收提醒，以及在渠道缺失或训练状态变化时系统如何用稳定中文提示处理。

本清单只新增验收口径，不要求立即实现接口、数据库、消息队列或移动端推送能力；也不阻塞当前正在运行的实现任务。

## 二、依据与用户路径

本清单参考现有训练计划完成率门禁、活动报名与签到口径、训练完成智能复盘卡片规格、训练异常提醒规则配置样例、跑步数据导入与活动瀑布流联调手册，梳理提醒偏好可能影响的用户路径。

| 用户路径 | 提醒偏好影响点 | 相关验收重点 |
|---|---|---|
| 成员加入训练计划 | 是否默认开启训练提醒、是否展示隐私提示 | 默认状态、授权文案、可撤回 |
| 成员报名跑团活动 | 报名成功后是否建立训练前提醒 | 报名状态、活动时间、提前提醒 |
| 成员取消报名或活动取消 | 已排队提醒是否取消或改为取消通知 | 取消训练、重复提醒、状态同步 |
| 训练开始前 | 是否按成员设置的提前时间发送提醒 | 触发时机、免打扰、移动端文案 |
| 训练结束后 | 是否发送复盘入口或异常提醒 | 智能复盘、异常降级、隐私边界 |
| 导入跑步数据异常 | 是否提示补录、修正或人工确认 | 异常提醒、渠道缺失、降级策略 |
| 成员修改渠道 | 邮箱、短信、站内信、移动推送缺失时如何处理 | 渠道优先级、失败提示、兜底 |
| 成员启用免打扰 | 夜间或自定义时段内如何延后或静默 | 免打扰时段、本地时间、不可打扰 |

## 三、门禁总原则

1. 提醒偏好必须以成员可理解的中文呈现，不能展示技术字段名或调度队列内部状态。
2. 默认状态必须明确，不允许“看起来开启、实际未发送”或“用户未同意却主动打扰”。
3. 所有提醒必须可追溯到训练计划、活动报名、签到、跑步数据导入或复盘结果，不能凭空生成。
4. 免打扰、渠道缺失、取消训练和重复触发必须有降级策略，不能静默失败。
5. 普通成员只能看到自己的提醒设置和训练提醒，不得暴露他人训练、联系方式或原始定位轨迹。
6. 移动端提醒文案必须短、准、可操作，不能依赖桌面端长说明才能理解。

## 四、验收检查项

### 1. 默认关闭或默认开启状态清晰

通过标准：系统必须在成员首次进入训练提醒偏好页面、训练计划报名流程或活动报名成功页明确展示默认状态。若默认关闭，应提示“你可以开启训练提醒”；若默认开启，应说明会发送哪些提醒、通过什么渠道发送，以及如何关闭。

失败示例：页面只显示“提醒偏好：是”，没有说明是训练前提醒、复盘提醒还是异常提醒；成员未授权移动推送却收到训练前推送。

建议验证方式：用新成员账号进入训练计划和活动报名流程，截图确认默认状态、说明文案和关闭入口；检查接口返回的默认布尔值、渠道列表和中文展示是否一致。

适合跟进的 worker：frontend-dev、backend-dev、test-engineer。

### 2. 提前提醒时间按训练或活动开始时间计算

通过标准：提前提醒必须基于训练计划或活动的开始时间计算，至少覆盖“训练开始前十分钟”“训练开始前三十分钟”“训练开始前一天”三类样例。活动时间缺失或格式异常时，不得创建无法解释的提醒，应展示“训练时间待确认，暂不发送提前提醒”。

失败示例：活动开始时间为晚上七点，系统按报名时间发送提醒；跨天训练被提前到错误日期提醒；活动时间为空时仍发送“今天训练即将开始”。

建议验证方式：构造当天、次日、跨天和缺失开始时间样例，断言调度时间、中文提示和接口降级状态；人工核对提醒时间与活动详情页时间一致。

适合跟进的 worker：backend-dev、test-engineer。

### 3. 免打扰时段必须优先于普通提醒

通过标准：成员设置免打扰时段后，训练提醒不得在该时段内直接打扰。可根据产品策略延后到免打扰结束后发送、提前到免打扰开始前发送，或仅保留站内未读提示，但必须在偏好页明确说明。

失败示例：成员设置晚上十点到早上七点免打扰，系统仍在凌晨六点推送“训练即将开始”；或者提醒被静默丢弃，成员完全不知道为何没有收到。

建议验证方式：设置覆盖训练前提醒时间的免打扰窗口，检查发送记录、站内信记录和页面说明；测试本地时区、跨午夜免打扰和全天免打扰三类样例。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer。

### 4. 渠道缺失时提供可理解降级

通过标准：当成员缺少手机号、邮箱、移动推送授权或站内通知能力时，系统必须展示中文降级提示，并优先使用仍可用的渠道。没有任何可用渠道时，不应标记为“提醒已开启”，而应提示“请先补充通知方式”。

失败示例：成员没有绑定邮箱，页面仍显示“邮件提醒已开启”；推送授权失败后没有站内提示；发送失败日志只写内部错误码，成员看不到原因。

建议验证方式：分别移除手机号、邮箱、移动推送授权和全部渠道，检查偏好页状态、发送队列状态和中文失败提示；确认不会泄露完整手机号或邮箱。

适合跟进的 worker：backend-dev、frontend-dev、security-reviewer、test-engineer。

### 5. 训练取消或报名取消后不再发送原训练提醒

通过标准：当活动取消、训练计划取消、成员取消报名或报名被管理员移除时，原本排队的训练前提醒必须取消或转为取消通知。取消通知应说明原因和下一步，不能继续提示“训练即将开始”。

失败示例：成员取消报名后仍收到训练前十分钟提醒；活动已取消但移动端仍显示原地点集合；取消通知没有说明是活动取消还是个人报名取消。

建议验证方式：在活动报名成功后创建提醒，再执行成员取消报名、管理员取消活动、训练计划删除三类操作，断言原提醒不再发送，并检查取消提示文案。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer。

### 6. 重复提醒必须去重并可追踪

通过标准：同一成员、同一训练或活动、同一提醒类型和同一触发时间只能产生一条有效提醒。重复报名、重复导入跑步数据、页面多次刷新或后台任务重试不得导致重复打扰。

失败示例：成员反复打开活动详情页后收到三条相同提醒；后台重试把同一条训练前提醒发送两次；复盘生成后重复发送相同异常提醒。

建议验证方式：模拟重复报名、重复提交偏好、调度任务重试和跑步数据重复导入，检查去重键、发送记录数量和用户收到的通知数量。

适合跟进的 worker：backend-dev、test-engineer。

### 7. 隐私提示与权限边界明确

通过标准：提醒偏好页必须说明通知会使用哪些渠道和哪些训练信息。提醒内容不得包含密码、完整手机号、完整邮箱、原始定位轨迹、其他成员训练详情或管理员内部备注。普通成员不能读取或修改他人的提醒偏好。

失败示例：训练提醒正文包含他人缺席名单；接口允许成员通过修改成员标识关闭别人提醒；异常提醒暴露原始定位坐标数组或内部风控原因。

建议验证方式：执行普通成员访问自己与他人偏好的权限测试；安全检查提醒样例、接口响应和页面渲染，确认无敏感字段泄露；人工核对隐私提示是否在开启前可见。

适合跟进的 worker：security-reviewer、backend-dev、frontend-dev、test-engineer。

### 8. 移动端文案短句、中文、可操作

通过标准：移动端提醒标题和正文必须为中文，标题应说明训练或活动名称，正文应包含时间、地点或下一步动作之一。长文案在窄屏下不能遮挡按钮；异常和取消场景必须有文字说明，不只依赖颜色或图标。

失败示例：移动端通知标题显示“training_reminder”；正文只写“click here”；取消训练提醒只有灰色图标没有文字；长文案把“关闭提醒”按钮挤出屏幕。

建议验证方式：用三百七十五像素宽度检查训练前提醒、取消提醒、异常提醒和复盘入口提醒；抽查通知中心、站内信列表和活动详情页二次确认文案。

适合跟进的 worker：frontend-dev、content-reviewer、test-engineer。

### 9. 异常提醒和复盘提醒不得替代医疗建议

通过标准：训练异常提醒只能基于已有异常预检、复盘卡片数据质量或完成状态给出保守提示。涉及配速突变、距离异常、心率缺失或训练未完成时，文案应提示复核数据、注意恢复或联系团长确认，不得给出医疗诊断。

失败示例：系统因为配速偏慢提示“你可能受伤”；心率缺失时提示“身体风险很高”；数据缺失时仍生成确定性训练建议。

建议验证方式：构造配速突变、距离异常、心率缺失、训练未完成和数据不足样例，检查异常提醒是否来自规则配置，并人工核对中文语气克制。

适合跟进的 worker：backend-dev、content-reviewer、test-engineer。

### 10. 用户修改偏好后即时生效且有确认反馈

通过标准：成员开启、关闭或修改提前时间、免打扰时段、渠道选择后，系统必须给出中文确认反馈，并使后续待发送提醒使用最新设置。已发送提醒不可撤回，但待发送提醒必须更新或取消。

失败示例：成员关闭提醒后，旧队列仍继续发送；页面保存成功但刷新后恢复旧设置；接口成功返回却没有说明下一次训练将按新时间提醒。

建议验证方式：修改偏好后立即读取接口状态，检查待发送提醒队列或模拟发送结果；验证关闭提醒、修改提前时间、修改免打扰时段和切换渠道四类操作。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer。

### 11. 报名、签到、训练完成状态必须一致

通过标准：提醒逻辑必须区分已报名、已签到、已完成训练、未完成训练和无法判断。报名成功可以触发训练前提醒；签到或跑步数据可以触发复盘提醒；未完成或无法判断时只能发送确认或补录提示，不能祝贺完成。

失败示例：成员报名后未到场，系统仍发送“训练完成”类提醒；签到但无跑步记录时直接推送复盘完成结论；状态不一致时没有任何中文提示。

建议验证方式：构造已报名未签到、已签到但无跑步记录、实际距离低于目标距离、无法判断四组样例，断言提醒类型、文案和状态同步一致。

适合跟进的 worker：backend-dev、frontend-dev、test-engineer。

### 12. 门禁摘要可直接贴到 kanban 评论

通过标准：文档末尾需提供一段可直接复制的中文摘要，概括本清单的验收目标、关键边界和建议跟进角色，便于直接粘贴到 kanban 评论。

失败示例：文档只有长表格，没有可复制摘要；摘要只写英文或只列文件名，无法让后续 worker 快速理解。

建议验证方式：人工复制摘要到 kanban 评论试贴，确认无需再改写即可读懂。

适合跟进的 worker：quality-gate、frontend-dev、backend-dev、test-engineer。

## 五、门禁摘要

训练提醒偏好验收清单聚焦成员是否能清楚设置并理解训练计划、活动报名和异常复盘的提醒规则；必须同时覆盖默认状态、提前提醒、免打扰、渠道降级、取消报名后停发、重复提醒去重、隐私边界、移动端中文文案、异常提醒克制、偏好修改即时生效与报名/签到/完成状态一致性。建议优先跟进 backend-dev、frontend-dev、test-engineer 和 security-reviewer，直接围绕接口返回、页面文案、发送队列和权限边界做自动化与人工验收。
