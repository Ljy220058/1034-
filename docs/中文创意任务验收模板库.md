# 中文创意任务验收模板库

适用项目：`/root/autodl-tmp/projects/hermes-swarm-lab`

本模板库用于快速创建中文 kanban 创意任务卡。每个模板都把“标题、描述、目标、输入、交付物、验收标准、建议 worker”拆开，便于创意生成器、人工调度者或 reviewer 复用。

## 使用边界

1. 本库只提供任务验收模板，不修改线上调度配置。
2. 创建任务前必须检查近期 kanban 和 `docs/` 产物，避免重复。
3. 本库刻意避开以下既有活动任务主题：
   - 跑步数据导入
   - 深圳技术大学风格
   - 瀑布流
4. 如果任务只是补充或评审已有产物，标题必须明确包含“补充”“评审”或“复核”，不要伪装成全新实现任务。
5. 目标产物路径必须唯一，且同一批次内不要给同一 worker 连续分配同类型任务。

## 任务卡通用字段

每张 kanban 卡建议包含：

- `title`：中文标题，使用对应模板填充。
- `assignee`：建议 worker 或实际 profile。
- `body`：中文描述，至少包含目标、输入、交付物、验收标准。
- `workspace_kind`：固定为 `dir`。
- `workspace_path`：固定为 `/root/autodl-tmp/projects/hermes-swarm-lab`。
- `priority`：0-10，越高越优先。
- `template_id`：模板编号。
- `artifact_path`：目标交付物路径。
- `dedupe_checks`：创建前去重检查。

## 模板 1：前端任务

模板编号：`frontend_acceptance`

建议标题：

```text
中文创意：{页面或模块}前端验收与体验优化
```

描述模板：

```text
目标：为{目标用户}完善{页面或模块}的前端体验和验收标准，确保入口、状态、异常提示都能被后续 worker 复核。

输入：
1. 页面或模块：{页面或模块}
2. 目标用户：{目标用户}
3. 入口位置：{入口位置}
4. 需要覆盖的交互状态：{交互状态列表}
5. 参考文件或现有说明：{参考文件}

交付物：
1. 前端方案或轻量实现，优先放在 frontend/ 或 docs/ 下。
2. 中文验收清单，写明打开页面、触发状态、观察结果。
3. 若修改代码，补充最小测试或手动验证记录。

验收标准：
1. 入口位置、默认态、加载态、空态、错误态描述完整。
2. 中文错误提示能指导用户下一步操作。
3. 交付物路径明确，不与既有“瀑布流”“深圳技术大学风格”相关任务重复。
4. reviewer 可按清单在 5 分钟内完成复核。

建议 worker：frontend-dev、ui-reviewer、具备前端/界面/交互能力的 worker。
```

创建前去重检查：

- 是否已有同页面、同入口、同交互状态任务。
- 是否会重复 `frontend/activity-waterfall.js` 或 `docs/深技大活动瀑布流界面规范清单.md` 相关主题。
- 是否已有同名 `docs/*前端*`、`docs/*界面*`、`docs/*入口*` 产物。

## 模板 2：后端任务

模板编号：`backend_acceptance`

建议标题：

```text
中文创意：{接口或服务}后端接口验收
```

描述模板：

```text
目标：实现或设计{接口或服务}，并给出字段、权限、错误处理和验收方法，支撑{业务场景}。

输入：
1. 接口或服务名称：{接口或服务}
2. 业务场景：{业务场景}
3. 接口路径：{接口路径}
4. 请求字段：{请求字段}
5. 返回字段：{返回字段}
6. 权限要求：{权限要求}

交付物：
1. 后端代码或接口说明文档。
2. 至少一个成功示例和一个失败示例。
3. 最小测试用例或可复测命令。

验收标准：
1. 字段定义、类型、必填性和默认值清楚。
2. 权限边界明确，越权、缺参、资源不存在都有中文错误说明。
3. 如改代码，相关测试通过；如只写方案，方案足以拆出实现任务。
4. 不重复已有“跑步数据导入”接口、导入错误提示或数据预检任务。

建议 worker：backend-dev、api-engineer、具备 FastAPI/SQLite/数据模型能力的 worker。
```

创建前去重检查：

- 是否已有相同接口路径或相同路由文件任务。
- 是否与 `backend/import_error_copy.py`、`tests/test_running_data_import_*` 相关导入任务重复。
- 是否只是测试补充；如果是，应改用测试模板。

## 模板 3：测试任务

模板编号：`test_acceptance`

建议标题：

```text
中文创意：{被测对象}测试验收清单
```

描述模板：

```text
目标：为{被测对象}建立可执行的测试与质量门禁，使后续 worker 能用统一标准判断任务是否完成。

输入：
1. 被测对象：{被测对象}
2. 测试范围：{测试范围}
3. 最小用例：{成功路径、失败路径、边界输入}
4. 失败提示要求：{失败提示要求}
5. 复测命令：{复测命令}

交付物：
1. tests/ 下的自动化测试，或 docs/ 下的中文冒烟清单。
2. 复测命令和预期结果。
3. 对不可自动化部分给出人工验证步骤。

验收标准：
1. 至少覆盖成功路径、失败路径、边界输入三类用例。
2. 失败信息能定位到字段、接口、页面或文档章节。
3. 复测命令可直接执行，或人工步骤足够明确。
4. 不重复已有训练计划日历导出、跑步数据导入、活动瀑布流等验收清单。

建议 worker：qa-tester、test-engineer、quality-gate、具备 pytest/冒烟/验收能力的 worker。
```

创建前去重检查：

- 是否已有同对象 `tests/test_*` 或 `docs/*验收*`、`docs/*冒烟*`。
- 上游实现或方案是否已经存在；如果不存在，应先创建前端、后端或文档任务。
- 是否只是在旧清单上换标题。

## 模板 4：文档任务

模板编号：`docs_acceptance`

建议标题：

```text
中文创意：{方案主题}中文方案与验收文档
```

描述模板：

```text
目标：为{目标读者}整理{方案主题}中文文档，作为后续实现、测试或评审任务的依据。

输入：
1. 方案主题：{方案主题}
2. 目标读者：{目标读者}
3. 必含章节：{必含章节}
4. 参考资料：{参考资料}
5. 与已有文档的区别：{区别说明}

交付物：
1. docs/ 下的 Markdown 文档。
2. 至少一个可拆分的后续任务建议。
3. 最小验收步骤，说明如何检查章节完整性和可执行性。

验收标准：
1. 全文中文，结构清晰，章节完整。
2. 每个关键建议都有可执行下一步。
3. 说明与已有文档的关系，不重复“跑步数据导入、深圳技术大学风格、瀑布流”活动任务。
4. 目标产物路径明确，能被 kanban reviewer 直接打开复核。

建议 worker：docs-writer、product-planner、creative-writer、具备中文写作/方案设计能力的 worker。
```

创建前去重检查：

- 是否已有相同主题 `docs/*.md`。
- 是否只是把“方案、说明、路线图、用户故事”互换标题。
- 如果是补充旧文档，标题和描述是否明确补充范围。

## 模板 5：安全审计任务

模板编号：`security_audit_acceptance`

建议标题：

```text
中文创意：{审计对象}安全审计与风险复核
```

描述模板：

```text
目标：审计{审计对象}在{审计范围}内的安全、权限或合规风险，并输出可复核的中文结论。

输入：
1. 审计对象：{审计对象}
2. 审计范围：{审计范围}
3. 风险分级标准：{风险分级标准}
4. 证据格式：{证据格式}
5. 整改建议格式：{整改建议格式}

交付物：
1. docs/ 下的 security-audit 或 review Markdown 报告。
2. 每条发现包含证据位置、影响、风险等级、是否阻塞、整改建议。
3. 最小复核步骤；如需修复，创建下游修复任务而不是在审计任务中直接扩范围。

验收标准：
1. 风险分级一致，证据可定位到文件、接口、字段或流程。
2. 整改建议可执行，且区分阻塞与非阻塞问题。
3. 不泄露密钥、token、原始 PII。
4. 不重复已有成员权限、认证 token、密码哈希、附件路径等安全审计报告。

建议 worker：security-reviewer、code-reviewer、compliance-reviewer、具备安全/权限/合规能力的 worker。
```

创建前去重检查：

- 是否已有同对象 `docs/security-audit-*` 或 `docs/review-*`。
- 是否与进行中的实现任务缺少上下游关系。
- 是否把同一对象反复创建为“审计、合规清单、风险评分”三种近似任务。
