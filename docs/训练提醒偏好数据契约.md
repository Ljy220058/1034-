# 训练提醒偏好数据契约

日期：2026-06-06
状态：最小可用契约
契约版本：训练提醒偏好.v1
适用范围：成员按训练计划、活动报名、异常复盘配置提醒偏好；后端生成提醒任务与前端展示设置页共用。

## 一、现有依据与边界

本契约只定义“成员提醒偏好”的最小数据结构，不修改线上配置，不新增数据库表，不替代已有复盘卡片、异常规则或活跃度分层模型。

| 依据 | 当前口径 | 本契约如何避免重复 |
|---|---|---|
| `backend/models.py` | `MemberBase` 包含成员基础资料和训练目标；`ActivityBase` 包含活动开始时间、距离、配速组；`RegistrationOut` 包含活动报名；`AttendanceOut` 包含签到状态 | 本契约只保存成员对不同提醒类型的接收偏好，不重新定义成员、活动、报名、签到字段 |
| `backend/database.py` | 当前核心表为 `members`、`activities`、`registrations`、`attendances`、`announcements` | 本契约不要求立即落库；若后续落库，应由数据库任务另写迁移和回滚脚本 |
| `docs/训练完成智能复盘卡片数据契约.md` | 已定义训练完成后的复盘卡片字段、异常标签和降级策略 | 本契约只决定“是否提醒、通过什么渠道、提前多久提醒”，不定义复盘内容 |
| `docs/训练异常提醒规则配置样例.md` | 已定义异常规则、严重级别、命中文案和适用模块 | 本契约只记录成员是否接收异常复盘提醒，不重复定义异常规则阈值 |
| `docs/跑团成员活跃度分层模型.md` | 已定义活跃度分层、召回场景和运营动作 | 本契约不计算成员分层，只允许后端在缺省偏好时参考成员分层做保守降级 |
| `docs/活动提醒智能摘要方案.md` | 已定义管理员活动提醒摘要，不面向普通成员个性化提醒 | 本契约面向成员个人提醒偏好，不生成活动管理摘要 |

## 二、实体关系口径

当前最小实体关系：

- `members`：提醒偏好的归属主体，使用 `members.id` 作为 `成员ID`。
- `activities`：活动报名提醒、活动开始前提醒的来源。
- `registrations`：判断成员是否报名某活动，用于活动提醒。
- 训练计划：当前仓库没有正式训练计划表，训练计划提醒可先使用前端训练模板、活动字段或后端计划服务的外部计划标识。
- 异常复盘：复用既有训练异常规则和智能复盘卡片的命中结果，只在命中后按成员偏好决定是否触达。

本契约建议对象名：`训练提醒偏好`。同一成员可以拥有多条偏好，每条偏好对应一个提醒类型。后续落库时建议用 `成员ID + 提醒类型` 建唯一约束，避免同一类型配置重复。

## 四、字段明细

| 字段 | 类型 | 必填 | 默认值 | 来源 | 缺失时降级策略 |
|---|---|---:|---|---|---|
| `契约版本` | 字符串 | 是 | `训练提醒偏好.v1` | 后端常量或前端配置常量 | 不允许缺失；后端拒绝保存，前端提示“提醒偏好版本缺失” |
| `成员ID` | 正整数 | 是 | 无 | `members.id`、当前登录成员上下文 | 不允许缺失；后端不生成个人提醒，前端不展示保存按钮 |
| `提醒类型` | 枚举字符串 | 是 | `训练计划` | 前端设置入口、后端默认偏好生成逻辑 | 缺失时按 `训练计划` 处理，但保存前必须补齐显式值 |
| `提醒渠道` | 字符串数组 | 是 | `["应用内"]` | 成员设置页；也可由后端按可用渠道初始化 | 缺失或为空时降级为 `["应用内"]`；不可用渠道应被后端过滤 |
| `提前时间分钟` | 非负整数 | 是 | `60` | 成员设置页、提醒类型默认值 | 缺失时训练计划用 60 分钟，活动报名用 120 分钟，异常复盘用 0 分钟 |
| `免打扰时段` | 对象 | 是 | 见子字段默认值 | 成员设置页 | 缺失时视为未启用免打扰，避免漏发重要提醒 |
| `免打扰时段.启用` | 布尔值 | 是 | `false` | 成员设置页开关 | 缺失时为 `false` |
| `免打扰时段.开始时间` | `HH:mm` 字符串或 `null` | 是 | `null` | 成员设置页 | 启用免打扰但缺失开始时间时，后端按未启用处理，并记录配置待修正 |
| `免打扰时段.结束时间` | `HH:mm` 字符串或 `null` | 是 | `null` | 成员设置页 | 启用免打扰但缺失结束时间时，后端按未启用处理，并记录配置待修正 |
| `免打扰时段.时区` | 字符串 | 是 | `Asia/Shanghai` | 系统默认时区或成员设置页 | 缺失时使用 `Asia/Shanghai`；未知时区按服务器默认时区降级 |
| `训练日例外` | 对象数组 | 是 | `[]` | 成员设置页、训练日历例外配置 | 缺失时为空数组；不影响常规提醒 |
| `训练日例外[].日期` | `YYYY-MM-DD` 字符串 | 是（数组项内） | 无 | 成员设置页选择的日期 | 单条例外日期缺失时忽略该例外项 |
| `训练日例外[].处理方式` | 枚举字符串 | 是（数组项内） | `暂停提醒` | 成员设置页 | 缺失时按 `暂停提醒`，避免在用户标记例外日继续打扰 |
| `训练日例外[].原因` | 字符串或 `null` | 是（数组项内） | `null` | 成员手工输入 | 缺失时为 `null`；前端显示“未填写原因”即可 |
| `是否启用` | 布尔值 | 是 | `true` | 成员设置页开关、后端默认偏好 | 缺失时为 `true`；若成员明确关闭过，必须以后端保存值为准 |
| `更新时间` | 日期时间字符串 | 是 | 当前保存时间 | 后端写入或更新时生成 | 缺失时后端保存前补当前时间；前端展示时可显示“刚刚更新” |

## 五、枚举约定

### 5.1 `提醒类型`

| 值 | 中文说明 | 适用数据来源 | 默认提前时间 |
|---|---|---|---:|
| `训练计划` | 成员个人训练计划、训练模板、计划日历中的训练日提醒 | 训练模板、活动字段、未来训练计划服务 | 60 |
| `活动报名` | 已报名活动的开始前提醒、集合信息提醒 | `registrations`、`activities` | 120 |
| `异常复盘` | 训练完成后命中异常规则或复盘降级时提醒成员查看 | 训练异常规则、智能复盘卡片 | 0 |

### 5.2 `提醒渠道`

| 值 | 中文说明 | 降级策略 |
|---|---|---|
| `应用内` | 系统内通知或消息中心 | 默认渠道，始终保留 |
| `短信` | 手机短信 | 手机号缺失或短信服务不可用时降级为 `应用内` |
| `邮件` | 电子邮件 | 当前成员模型没有邮箱字段；后端未支持前不得启用，启用失败时降级为 `应用内` |
| `微信` | 微信或企业微信提醒 | 当前没有微信绑定字段；未绑定时降级为 `应用内` |

### 5.3 `训练日例外[].处理方式`

| 值 | 中文说明 | 适用场景 |
|---|---|---|
| `暂停提醒` | 该日期不发送本类型提醒 | 请假、休息日、旅行 |
| `仅应用内` | 该日期只保留应用内提醒，不走外部渠道 | 免打扰但仍想留系统记录 |
| `提前一天` | 该日期的提醒提前到前一天同一时间或默认时间发送 | 比赛日、长距离训练日前准备 |

## 六、降级与冲突处理规则

1. 成员没有任何提醒偏好时，后端可生成三条默认偏好：训练计划、活动报名、异常复盘，渠道均为 `应用内`，全部启用。
2. 同一成员同一提醒类型只能有一条生效偏好；若输入重复，后端应以后 `更新时间` 最新的一条为准，并在落库设计中使用唯一约束防止重复。
3. 免打扰时段只延后或压制外部渠道，不应删除应用内提醒记录。
4. 异常复盘提醒的 `提前时间分钟` 默认为 0，表示异常结果生成后即可提醒；若处于免打扰时段，短信、微信、邮件延后到免打扰结束后发送。
5. 活动报名提醒只对 `registrations.status = 'registered'` 的记录生效；取消报名后不再发送活动报名提醒。
6. 若提醒渠道全部不可用，后端必须保留 `应用内`，避免完全静默。
7. 当前没有正式训练计划表时，训练计划提醒可使用活动训练日、前端训练模板或外部计划标识作为触发来源；本契约不规定计划表结构。

## 十、后续复用方式

### 10.1 backend-dev 复用方式

1. 将 `schemas/training_reminder_preference.schema.json` 作为请求体验证依据，新增或更新 Pydantic 模型时保持字段名、枚举值、默认值和降级策略一致。
2. 生成提醒任务时，先按 `成员ID + 提醒类型` 读取偏好；没有配置时使用本文默认偏好。
3. 活动报名提醒只读取 `registrations.status = 'registered'` 和 `activities.start_time`，不重复计算活动摘要。
4. 异常复盘提醒只消费异常规则或复盘卡片输出，不重新定义异常阈值。
5. 后续如需落库，建议新增独立表保存偏好，并为 `member_id` 建外键和索引，为 `member_id + reminder_type` 建唯一约束；迁移脚本必须带对应回滚脚本。

### 10.2 frontend-dev 复用方式

1. 设置页按本文字段展示：提醒类型、提醒渠道、提前时间、免打扰、训练日例外、是否启用。
2. 前端提交前可用 `schemas/training_reminder_preference.schema.json` 中的枚举和必填字段做轻量校验。
3. 文案应使用本文中文枚举，不在前端自造同义值，避免后端无法识别。
4. 当外部渠道不可用时，前端提示“将降级为应用内提醒”，但不要删除用户选择，最终以后端返回为准。
5. 第三条样例可作为免打扰设置页的手工验收样例。

## 十一、后续落库建议

当前任务只交付数据契约，不新增数据库表。若后续需要持久化，建议表名为 `training_reminder_preferences`，核心约束如下：

- 主键：`id INTEGER PRIMARY KEY AUTOINCREMENT`。
- 外键：`member_id INTEGER NOT NULL` 显式引用 `members(id)`，并建立 `idx_training_reminder_preferences_member_id`。
- 唯一约束：`member_id, reminder_type`，建议命名为 `uq_training_reminder_preferences_member_type`。
- JSON 字段：`channels`、`quiet_hours`、`training_day_exceptions` 可用 TEXT 保存 JSON，但必须由应用层按本契约校验。
- 常用查询索引：按成员读取全部偏好、按启用状态和提醒类型筛选待触达偏好。
- 所有迁移必须使用事务包裹，并提供回滚脚本。
