# 代码审查报告
## 严重（必须修）
- [backend/routes/workspaces.py:43-44] 仅用 `..` 作为路径穿越判定，未处理绝对路径拼接后的符号链接逃逸，攻击者可通过合法绝对路径指向工作区外的目录 → 建议：在 `resolve()` 后再校验路径是否仍落在允许的根目录下，或者只接受预注册 workspace 标识而不是任意路径。

## 中等（应该修）
- [backend/routes/workspaces.py:127-131] `/task-queue/workers` 读取接口没有做分页/上限，直接返回全部 worker；在 worker 数量增大时会放大响应体和数据库压力 → 建议：加 `limit/offset` 或至少默认分页，并在 repository 层限制返回规模。
- [backend/routes/tasks.py:101-130] `/workspaces/tasks` 端点虽然声明需要 `current_user`，但实际只要通过 `admin_or_leader` 即可访问，且异常时把所有 `ValueError` 都映射为 422，掩盖了调用方错误与服务端错误的边界 → 建议：拆分为明确的参数校验错误和内部错误，保留非预期异常继续上抛，避免误导客户端重试。
- [backend/repository.py:220-226] `create_task_queue_worker()` 在插入/更新时未对白名单状态做约束，虽然路由层目前校验了 `payload.status`，但 repository 可被其他调用路径直接复用，形成非法状态写入风险 → 建议：在 repository 层再次校验 status 白名单或依赖数据库 CHECK 约束并显式捕获 `IntegrityError`。

## 建议（可以修）
- [backend/app.py:25-27, 55-66] 统一把成功/失败响应包成 `{data, message}` / `{detail}`，但 root/health 的返回结构与 `/api/v1` 的响应风格不一致，前端和调用方需要分别处理两套协议 → 建议：明确 API 版本边界，或让所有公开接口统一 envelope。
- [backend/routes/workspaces.py:219-223] `TaskBoardItem.updated_at` 直接用 `datetime.fromisoformat()` 解析持久化值，遇到脏数据会在列表页抛异常导致整个板块不可用 → 建议：对单条记录做容错跳过或在入库时强制标准化时间格式。
- [backend/task_discovery.py:47-51] `_decode_metadata()` 把任意 JSON 解析失败都吞掉并返回原始字符串，后续 board 排序/过滤可能悄悄失效 → 建议：至少记录日志并区分“非 JSON 字符串”和“损坏数据”，便于排查数据污染。
