# 活动报名候补名单功能方案

## 1. 目标与范围

本方案面向 1034 跑团管理系统的“活动报名”场景，解决热门活动名额有限时成员无法排队的问题。

目标：
- 当活动名额未满时，成员报名后状态为“已报名”。
- 当活动名额已满时，成员可加入候补队列，状态为“候补中”。
- 当已报名成员取消报名时，系统按候补顺序自动补位最早加入候补的成员。
- 管理员和团长可查看某场活动的候补名单与排序。

不在本次范围内：
- 不接入短信、微信、邮件等第三方提醒。
- 不做在线支付、积分、抽签等扩展机制。
- 不新增复杂审批流。
- 不改造成独立活动容量管理模块。

## 3. 功能设计

### 3.1 名额规则

为活动增加可选名额上限：
- `capacity`：活动最大已报名人数，整数，可为空。
- 当 `capacity` 为空时，活动不限名额，报名行为与现有逻辑一致。
- 当 `capacity` 为正整数时，只统计 `registrations.status = 'registered'` 的人数作为已占用名额。
- `waitlisted` 状态不占用正式名额。
- `cancelled` 状态不占用名额。

建议约束：
- `capacity` 必须大于 0 或为空。
- 活动创建和修改时都允许设置 `capacity`。
- 如果后续把 `capacity` 调小到低于当前已报名人数，本期先不自动挤出成员，只禁止新的正式报名；新增报名进入候补。

### 3.2 报名状态

扩展报名状态：
- `registered`：已报名，占用正式名额。
- `waitlisted`：候补中，不占用正式名额。
- `cancelled`：已取消。

保留 `registrations` 表承载候补队列，不新增独立候补表，理由：
- 当前表已经有 `activity_id`、`member_id`、`status`、`created_at`，天然可以表达“某成员在某活动中的报名关系”。
- 候补顺序可以用进入候补时的时间和自增 ID 排序。
- 避免新增表导致实现范围过大。

### 3.3 候补排序

候补排序规则：
1. 优先按 `waitlisted_at` 升序。
2. `waitlisted_at` 相同时按 `id` 升序。

如果为了减少字段，也可以临时用 `created_at` 表示进入当前状态的时间；但推荐新增 `waitlisted_at`，避免与已报名时间、取消时间混淆。

### 3.4 自动补位规则

当成员取消正式报名时：
1. 将该成员报名状态改为 `cancelled`。
2. 查询同活动最早的 `waitlisted` 记录。
3. 如果存在候补记录，则将其状态改为 `registered`。
4. 返回取消者记录，并在响应中附带补位成员信息，方便前端提示。

建议响应示例：

```json
{
  "data": {
    "cancelled": {
      "id": 88,
      "activity_id": 10,
      "member_id": 1,
      "status": "cancelled"
    },
    "promoted": {
      "id": 91,
      "activity_id": 10,
      "member_id": 5,
      "status": "registered"
    }
  },
  "message": "成功"
}
```

为兼容现有前端或测试，也可以先保持 `data` 返回取消记录，并新增 `promoted_registration` 字段：

```json
{
  "data": {
    "id": 88,
    "activity_id": 10,
    "member_id": 1,
    "status": "cancelled",
    "promoted_registration": {
      "id": 91,
      "activity_id": 10,
      "member_id": 5,
      "status": "registered"
    }
  },
  "message": "成功"
}
```

推荐使用第二种，改动范围更小。

## 4. 需要新增或修改的数据字段

### 4.1 activities 表

新增字段：

```sql
ALTER TABLE activities ADD COLUMN capacity INTEGER CHECK (capacity IS NULL OR capacity > 0);
```

对应模型修改：
- `ActivityBase.capacity: Optional[int] = Field(default=None, gt=0)`
- `ActivityCreate.capacity`
- `ActivityUpdate.capacity`
- `ActivityOut.capacity`
- `repository.Activity.capacity`
- `_row_to_activity()` 与 `Activity.model_dump()` 输出 `capacity`

### 4.2 registrations 表

修改状态约束，支持 `waitlisted`。

当前 SQLite 不方便直接修改 CHECK 约束，建议通过迁移脚本重建表，或在初始化 SQL 中把约束改为：

```sql
status TEXT NOT NULL DEFAULT 'registered' CHECK (status IN ('registered', 'waitlisted', 'cancelled'))
```

新增字段：

```sql
ALTER TABLE registrations ADD COLUMN waitlisted_at TEXT;
ALTER TABLE registrations ADD COLUMN updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP;
```

字段含义：
- `waitlisted_at`：进入候补队列时间，仅 `status = 'waitlisted'` 时有值。
- `updated_at`：报名状态最后更新时间，便于后续排查和前端展示。

对应模型修改：
- `RegistrationStatus = Literal['registered', 'waitlisted', 'cancelled']`
- `RegistrationOut.waitlisted_at: Optional[datetime]`
- `RegistrationOut.updated_at: Optional[datetime]`
- `repository.Registration.waitlisted_at`
- `repository.Registration.updated_at`
- `_row_to_registration()` 和 `Registration.model_dump()` 输出新字段

## 5. 需要新增或修改的 API

### 5.1 修改 POST /activities

作用：创建活动时允许设置名额上限。

请求新增字段：
- `capacity`：可选整数，大于 0。

示例：

```json
{
  "title": "周六晨跑",
  "start_time": "2026-06-08T07:00:00+08:00",
  "location": "人民公园东门",
  "capacity": 20
}
```

验收要点：
- 管理员和团长可以创建带 `capacity` 的活动。
- 普通成员仍不能创建活动。
- `capacity = 0` 或负数返回 `422`。
- 不传 `capacity` 时表示不限名额。

### 5.2 修改 PATCH /activities/{activity_id}

作用：管理员或团长可修改名额上限。

请求新增字段：
- `capacity`：可选整数，大于 0；传 `null` 可清除名额限制。

验收要点：
- 修改后活动详情返回新 `capacity`。
- 将 `capacity` 清空后，后续报名不再进入候补。
- 将 `capacity` 调低到当前报名人数以下时，不自动取消任何已报名成员。

### 5.3 修改 GET /activities 与 GET /activities/{activity_id}

作用：返回活动容量与报名统计，方便前端展示名额状态。

响应建议新增字段：
- `capacity`：名额上限。
- `registered_count`：当前正式报名人数。
- `waitlisted_count`：当前候补人数。
- `available_slots`：剩余正式名额；不限名额时可返回 `null`。

示例：

```json
{
  "id": 10,
  "title": "周六晨跑",
  "capacity": 20,
  "registered_count": 20,
  "waitlisted_count": 3,
  "available_slots": 0
}
```

实现建议：
- 可以先在 repository 查询活动详情时额外聚合统计。
- 如果担心影响现有 `Activity` dataclass，也可以定义新的 `activity_to_payload(activity)` 辅助函数，在 routes 层补充统计字段。

### 5.4 修改 POST /activities/{activity_id}/registrations

作用：名额满时自动进入候补。

逻辑：
1. 校验活动存在、成员存在、权限合法。
2. 如果成员已有 `registered` 状态，返回 `409 member already registered for this activity`。
3. 如果成员已有 `waitlisted` 状态，返回 `409 member already waitlisted for this activity`。
4. 如果成员已有 `cancelled` 状态，允许重新报名或重新候补，并更新时间字段。
5. 如果活动不限名额，创建或更新为 `registered`。
6. 如果活动有限名额且当前 `registered_count < capacity`，创建或更新为 `registered`。
7. 如果活动有限名额且当前 `registered_count >= capacity`，创建或更新为 `waitlisted`，写入 `waitlisted_at`。

响应：
- 返回 `RegistrationOut`，其中 `status` 告知是 `registered` 还是 `waitlisted`。

错误：
- `404 activity not found`
- `409 member already registered for this activity`
- `409 member already waitlisted for this activity`
- `403 forbidden`

### 5.5 修改 DELETE /activities/{activity_id}/registrations/{member_id}

作用：取消报名或取消候补，并在取消正式报名时自动补位。

逻辑：
- 取消 `registered`：状态改为 `cancelled`，然后触发候补补位。
- 取消 `waitlisted`：状态改为 `cancelled`，不触发补位。
- 取消 `cancelled`：可返回 `404 registration not found` 或保持幂等返回已取消记录；为了兼容当前行为，建议返回已取消记录。

响应新增：
- 如果触发补位，返回补位记录。
- 如果没有补位，`promoted_registration` 为 `null` 或不返回该字段。

### 5.6 新增 GET /activities/{activity_id}/waitlist

作用：管理员或团长查看某场活动候补名单。

权限：
- 仅 `admin` 和 `leader` 可访问。
- 普通成员访问返回 `403 forbidden`。

返回排序：
- 按 `waitlisted_at ASC, id ASC`。

响应示例：

```json
{
  "data": [
    {
      "id": 91,
      "activity_id": 10,
      "member_id": 5,
      "member_name": "李四",
      "status": "waitlisted",
      "waitlist_position": 1,
      "waitlisted_at": "2026-06-06T08:30:00+08:00"
    }
  ],
  "message": "成功"
}
```

实现建议：
- 在 `backend/routes/activities.py` 增加路由。
- 在 `backend/repository.py` 增加 `list_activity_waitlist(activity_id)`。
- 查询时 LEFT JOIN `members`，返回 `member_name` 便于管理员查看。
- 如果活动不存在，返回 `404 activity not found`。

## 6. 需要新增或修改的页面

由于当前前端还不是完整业务后台，建议采用“小范围增量接入”：

### 6.1 活动列表/活动详情中的名额展示

作用对象：活动卡片或活动详情区块。

展示内容：
- 名额：`已报名/总名额`，例如 `20/20`。
- 候补：例如 `候补 3 人`。
- 剩余名额：例如 `剩余 2 个名额`。
- 不限名额活动展示 `不限名额`。

预期效果：成员报名前能判断是直接报名还是进入候补。

### 6.2 报名按钮状态

作用对象：活动详情页报名按钮。

展示规则：
- 有剩余名额：按钮文案为 `报名活动`。
- 名额已满：按钮文案为 `加入候补`。
- 本人已报名：按钮文案为 `取消报名`，并显示 `已报名` 标签。
- 本人候补中：按钮文案为 `取消候补`，并显示 `候补中` 标签。

预期效果：成员明确知道提交后的结果，不误以为候补就是正式报名。

### 6.3 管理员候补名单区块

作用对象：活动详情页的管理员/团长视图。

展示内容：
- 候补顺位。
- 成员姓名。
- 成员 ID。
- 加入候补时间。

交互：
- 进入活动详情时调用 `GET /activities/{activity_id}/waitlist`。
- 普通成员不展示该区块。
- 候补为空时展示空态：`暂无候补成员`。

预期效果：管理员无需查数据库即可知道候补顺序。

场景：

## 9. 边界条件

### 9.1 活动不存在

报名、取消、查看候补名单时，如果活动不存在：
- 报名返回 `404 activity not found`。
- 查看候补名单返回 `404 activity not found`。
- 取消报名保持现有语义，返回 `404 registration not found` 或改为更明确的 `404 activity not found`；建议优先兼容现有测试。

### 9.2 成员不存在

报名时成员不存在：
- 当前 `create_registration()` 对活动或成员不存在统一返回 `not_found`。
- API 当前对报名接口映射为 `404 activity not found`，语义不完全准确。
- 本期可保持兼容；如果要修正，建议使用 `404 activity or member not found`，但需要同步更新测试与文档。

### 9.3 取消后补位的事务一致性

取消正式报名和候补补位必须在同一个数据库事务内完成，避免出现：
- A 已取消但 B 未补位。
- 两个并发取消导致同一个候补成员被重复补位。

SQLite 场景下建议在同一个 `with connect() as connection` 内执行取消和补位。对于并发压力，本项目当前是轻量管理系统，可以先不引入显式锁；如果后续并发测试失败，再考虑 `BEGIN IMMEDIATE`。

### 9.4 重新报名

成员取消后再次报名：
- 如果有名额，状态从 `cancelled` 更新为 `registered`。
- 如果无名额，状态从 `cancelled` 更新为 `waitlisted`，并刷新 `waitlisted_at`。

### 9.5 签到限制

当前签到逻辑要求成员必须有 `registered` 状态。

候补成员不能签到：
- `create_attendance()` 当前只接受 `registration['status'] == 'registered'`，天然满足。
- 建议新增测试确认 `waitlisted` 成员签到返回 `409 member is not registered for this activity`。

### 9.6 删除活动或成员

当前外键已经设置：
- 删除活动会级联删除 registrations。
- 删除成员会级联删除 registrations。

候补记录继续使用 registrations 表，因此无需额外级联逻辑。

## 10. 验收标准

### 10.1 后端验收

- `POST /activities` 支持可选 `capacity`，非法容量返回 `422`。
- `GET /activities` 和 `GET /activities/{activity_id}` 返回 `capacity`、`registered_count`、`waitlisted_count`、`available_slots`。
- `POST /activities/{activity_id}/registrations` 在名额未满时返回 `registered`。
- `POST /activities/{activity_id}/registrations` 在名额已满时返回 `waitlisted`。
- 重复正式报名返回 `409 member already registered for this activity`。
- 重复候补返回 `409 member already waitlisted for this activity`。
- `DELETE /activities/{activity_id}/registrations/{member_id}` 取消正式报名后会自动补位最早候补成员。
- `GET /activities/{activity_id}/waitlist` 仅管理员和团长可访问，并按候补顺序返回。
- 候补成员不能签到。
- 不限名额活动保持现有报名行为。

### 10.2 前端验收
