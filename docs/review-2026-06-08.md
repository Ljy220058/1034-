# 代码审查报告
## 严重（必须修）
- [backend/routes/common.py:18-19] `TOKEN_TTL_HOURS=***` 直接落在源码里且语法异常，等于把认证密钥/配置位以占位符方式硬编码进仓库，当前文件也无法正常导入 → 建议：改为从环境变量或配置文件读取有效 TTL 配置，并删除源码中的占位符；同时补充启动时配置校验，避免服务在坏配置下静默启动。
- [backend/routes/workspaces.py:55-94] 工作区路径校验只允许 `PROJECT_ROOT` 或当前工作目录的子路径，但 `selector` 可被构造为任意 `workspace:` 前缀路径后再交给 `Path.resolve(strict=False)`；对于未初始化但存在符号链接/相对路径绕过时，边界校验不够稳健 → 建议：在解析前统一拒绝非绝对路径，解析后同时校验 `normalized == normalized.resolve()` 的可信根，使用预定义工作区根白名单而不是“项目根/当前目录”双重猜测。
- [backend/routes/announcements.py:18-23, backend/routes/common.py:265-272] 公告写入兼容旧字段时，把 `content/body` 两个字段双向同步并强制 `is_pinned=True`，这会让客户端输入被静默改写，且历史字段兼容策略不唯一；如果前端同时传两者，最终值取舍不透明，容易造成公告内容错写或覆盖 → 建议：明确唯一标准字段（例如只保留 `body`），对旧字段只做只读兼容映射；若同时出现 `content` 与 `body`，应返回 400 并提示冲突，而不是静默覆盖。

## 中等（应该修）
- [backend/routes/workspaces.py:188-224] 批量创建任务时对 `TaskItemCreate.model_validate(item)` 只捕获 `ValueError`，Pydantic 的结构化校验通常抛 `ValidationError`，这里会漏掉大部分非法输入并返回 500 → 建议：改为捕获 `ValidationError`，并统一转换为 422；同时对每个 item 返回具体错误位置，便于前端定位。
- [backend/routes/workspaces.py:205-239] `batch_create_task_items` 允许任意字符串 `workspace_path` 写入，只在后续仓储层做 `resolve()`，但没有限制是否属于当前用户可写工作区；这会把工作区写权限和读取权限混在一起，导致越权写入风险 → 建议：复用统一的工作区授权检查，在进入 upsert 前验证当前用户对目标 workspace 有写权限，并把允许写入的根目录收敛到单一配置。
- [backend/routes/common.py:133-147] `sanitize_member_payload` 通过 `payload.__class__.__name__ == 'UserRegister'` 区分注册/更新逻辑，依赖类名字符串，重构或继承后会失效；同时“首个用户可任意角色”的逻辑没有显式封装，后续维护很容易误改成默认越权 → 建议：改为显式类型判断（`isinstance`）或分离注册/更新两个入口；把 bootstrap 逻辑抽成单独函数并加测试覆盖。
- [backend/routes/members.py:27-31, 34-41] 创建/更新成员时，角色校验散落在路由层：`create_member_endpoint` 先拒绝非管理员创建高权限角色，但 `patch_member` 又允许先提交再把角色强制改回 member；这类“先接受再修正”会让审计和错误提示不一致 → 建议：在模型校验层统一限制可写字段，管理员与普通用户分别使用不同 schema；对不可接受的 role 直接 400/403，不要在 handler 里静默覆写。
- [backend/repository.py:405-423] `upsert_workspace_task_item` 的 `INSERT ... ON CONFLICT ... DO UPDATE` 依赖 `workspace, task_key` 唯一键，但返回行通过二次 `SELECT` 拉取，若并发下发生写入竞争，可能读到旧状态或其他事务结果 → 建议：在 SQLite 版本支持时使用 `RETURNING`，或在同一事务里用 `last_insert_rowid`/受影响行再次锁定；至少把写入和回读放在显式事务中。

## 建议（可以修）
- [backend/app.py:135-153] `RequestValidationError` 只返回第一条错误信息，丢掉了其余字段错误；对于复杂请求，这会降低排障效率 → 建议：保留完整 `errors()` 数组，或至少在 `detail` 中附带字段路径和错误码。
- [backend/app.py:164-171] `HTTPException` 处理器只在 `detail` 为 `dict` 且包含 `error` 时原样透传，否则统一包装为 `{'detail': ...}`，不同接口错误结构不一致；前端/调用方需要分支处理 → 建议：统一所有 API 错误响应结构，至少让 `detail`、`error_code`、`status_code` 始终存在。
- [backend/routes/announcements.py:12-15, 26-31, 34-50] 读取接口没有对公告正文做任何输出编码或 HTML 清洗；如果公告内容会在前端直接渲染，存在存储型 XSS 风险（取决于前端渲染方式） → 建议：后端返回纯文本并在前端做转义，或在写入时限制允许的标记集；如果前端使用 `innerHTML`，必须改为文本节点渲染。
