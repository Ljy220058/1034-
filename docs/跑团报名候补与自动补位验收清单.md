# 跑团报名候补与自动补位中文验收清单

## 背景与适用范围

本清单用于验收“跑团活动报名候补与自动补位”功能。编写时参考了现有《活动报名候补名单功能方案》、活动报名接口与用户指南、训练提醒偏好、通知失败降级、隐私字段展示等相关文档约束。目标是在实现前统一边界场景、中文提示、隐私保护和回归测试口径，避免候补队列上线后出现顺序错乱、重复报名、补位通知不可追踪或移动端提示不一致。

适用范围包括：成员报名、活动满员进入候补、正式成员取消后的自动补位、补位通知超时、管理员调整活动容量、候补名单可见字段、移动端中文提示与回归测试。本文只作为验收门禁清单，不包含代码实现。

## 验收检查项

### 1. 候补排序稳定且可解释

- 通过标准：活动满员后，新增成员进入候补队列；候补顺序优先按进入候补时间升序排列，同一时间再按记录编号升序排列；管理员和团长查看到的排序与系统实际补位顺序一致。
- 失败示例：后加入候补的成员排到前面；刷新页面后候补顺序变化；接口返回顺序与前端展示顺序不一致。
- 建议验证方式：准备一个名额已满的活动，连续让三名成员加入候补，检查接口返回、管理端列表和数据库记录顺序；重复刷新并断言顺序不变。
- 适合跟进的 worker：后端开发 worker、测试 worker。

### 2. 取消正式报名后自动补位第一位候补成员

- 通过标准：正式报名成员取消报名后，系统只补位候补队列第一位成员；被补位成员状态从“候补中”变为“已报名”；取消者状态为“已取消”；活动正式报名人数不超过名额上限。
- 失败示例：取消后无人补位；一次取消补位多名成员；补位后正式报名人数超过名额；取消者仍显示“已报名”。
- 建议验证方式：创建名额为二的活动，加入两名正式成员和两名候补成员，取消一名正式成员后检查状态、人数统计、补位成员和响应提示。
- 适合跟进的 worker：后端开发 worker、测试 worker。

### 3. 补位通知超时有明确降级与可追踪状态

- 通过标准：候补成员被自动补位后，系统尝试发送站内或配置渠道通知；通知超时或失败时，补位状态不回滚，系统记录失败原因，并在管理端或运维日志中给出“通知失败，已保留报名名额”的中文提示。
- 失败示例：通知失败导致补位成员又回到候补；接口一直等待通知返回导致取消报名请求超时；日志没有记录失败原因；用户端误提示“补位失败”。
- 建议验证方式：模拟通知服务超时、拒绝和不可达三种情况，检查报名状态不受影响、失败记录可查询、中文降级提示清楚且不暴露内部异常栈。
- 适合跟进的 worker：后端开发 worker、通知集成 worker、测试 worker。

### 4. 重复报名与重复候补被拦截

- 通过标准：同一成员在同一活动中只能存在一个有效报名关系；已报名成员再次报名时返回明确中文提示；候补中成员重复点击报名不会新增第二条候补记录；已取消成员重新报名时按当前活动容量重新判断“已报名”或“候补中”。
- 失败示例：同一成员同时出现在正式名单和候补名单；多次点击按钮生成多条候补记录；已取消成员重新报名仍被提示“已报名”。
- 建议验证方式：对同一成员连续调用报名接口，分别覆盖已报名、候补中、已取消后重新报名三类状态，断言记录唯一且提示文案正确。
- 适合跟进的 worker：后端开发 worker、前端开发 worker、测试 worker。

### 5. 活动满员时新报名自动进入候补而不是失败退出

- 通过标准：设置名额上限的活动在正式报名人数达到上限后，新成员报名返回“候补中”状态和候补排序；不限名额活动保持原有直接报名行为；容量为空和容量为正整数的逻辑清晰区分。
- 失败示例：满员后报名直接返回错误且不进入候补；不限名额活动错误地进入候补；候补成员占用正式名额导致人数统计异常。
- 建议验证方式：分别创建不限名额活动和名额为一的活动，验证满员前、满员后、候补加入后的接口响应、人数统计和前端标签。
- 适合跟进的 worker：后端开发 worker、前端开发 worker、测试 worker。

### 6. 管理员扩容后候补处理规则一致

- 通过标准：管理员调高活动名额后，系统按产品约定处理候补队列：若支持自动补位，则按候补顺序补齐新增名额；若不自动补位，则明确提示“扩容后新报名优先补位规则待管理员确认”，且不会打乱已有候补顺序。规则必须在接口、管理端和用户指南中一致。
- 失败示例：扩容后随机挑选候补成员补位；扩容后候补顺序被重置；前端显示还有名额但候补成员仍无法补位且无说明。
- 建议验证方式：构造名额为二且有三名候补的活动，将名额扩为四，检查补位人数、补位顺序、候补剩余列表、管理员提示和文档说明一致。
- 适合跟进的 worker：产品规格 worker、后端开发 worker、前端开发 worker、测试 worker。

### 7. 候补名单隐私字段默认隐藏

- 通过标准：普通成员只能看到自己的报名或候补状态、候补排位和必要活动信息；不得看到其他候补成员的手机号、邮箱、微信号、证件号、完整姓名等隐私字段；管理员和团长查看敏感字段也应遵循最小必要原则，并保留权限边界。
- 失败示例：普通成员可下载完整候补名单；接口向移动端返回其他成员手机号；通知失败日志包含完整联系方式；截图分享页暴露候补成员真实姓名列表。
- 建议验证方式：分别使用普通成员、团长、管理员身份请求候补名单接口和页面，检查响应字段、页面渲染、日志内容和导出内容是否做脱敏或隐藏。
- 适合跟进的 worker：安全审计 worker、后端开发 worker、前端开发 worker。

### 8. 移动端中文文案清楚区分“已报名、候补中、已补位、已取消”

- 通过标准：移动端活动详情、报名按钮、候补标签、取消确认弹窗、补位成功提示和通知失败降级提示均为自然中文；不同状态的按钮和提示不混淆；关键动作前有确认，动作后有结果反馈。
- 失败示例：候补中仍显示“立即报名”；补位成功提示使用英文；取消报名后只显示空白；通知失败时显示“系统错误”而不是可理解的降级说明。
- 建议验证方式：用移动端宽度或真机浏览器走完整流程，截图核对各状态中文文案；对失败态注入接口错误，检查提示是否可理解且不泄露技术细节。
- 适合跟进的 worker：前端开发 worker、中文文案 worker、测试 worker。

### 9. 取消候补不影响正式名单和其他候补顺序

- 通过标准：候补中成员主动取消候补时，只将自己的状态改为“已取消”或移出候补视图，不触发正式成员变化；排在其后的候补成员相对顺序保持不变，排位可按展示规则更新。
- 失败示例：候补成员取消后错误触发补位；正式报名人数变化；后续候补成员顺序被重新随机排序；取消者仍占据候补排位。
- 建议验证方式：准备一个满员活动和三名候补成员，取消第二名候补，检查正式名单、候补剩余顺序、排位展示和取消提示。
- 适合跟进的 worker：后端开发 worker、前端开发 worker、测试 worker。

### 10. 回归测试覆盖不限名额、满员、候补、补位和通知降级

- 通过标准：自动化测试至少覆盖不限名额直接报名、满员进入候补、重复报名拦截、取消正式报名自动补位、取消候补不补位、管理员扩容、通知失败降级、隐私字段隐藏和移动端关键文案；测试命名能看出业务场景。
- 失败示例：只测接口成功路径；没有测试通知失败；没有普通成员权限下的隐私字段断言；改动后旧的活动报名测试被跳过或删除。
- 建议验证方式：运行后端接口测试、前端状态渲染测试和必要的端到端冒烟脚本，检查失败用例是否能定位到具体业务场景。
- 适合跟进的 worker：测试 worker、后端开发 worker、前端开发 worker。

## 可复制到 kanban 评论的门禁摘要

候补与自动补位验收门禁摘要：需覆盖候补排序、取消正式报名后的第一候补补位、补位通知超时降级、重复报名拦截、满员进入候补、管理员扩容规则、隐私字段隐藏、移动端中文文案、取消候补不误补位和回归测试。每项需同时给出通过标准、失败示例、验证方式和跟进 worker；若 pytest 未全绿、制品路径缺失、隐私字段泄露或导入失败，应判定为不通过并创建修复任务。
