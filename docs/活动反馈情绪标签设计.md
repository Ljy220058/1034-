# 活动反馈情绪标签设计

## 1. 目标与边界

活动反馈情绪标签用于在活动结束后，把成员提交的中文反馈快速归类为可运营的信号，帮助团长和管理员识别满意点、困惑点、风险点与改进建议。

本方案只产出设计文档，不修改业务代码。首版不依赖第三方 API，不使用 AI/LLM，不强制新增数据库表；如果项目短期尚未实现反馈提交功能，可以先把本方案作为后续活动复盘或反馈模块的字段规范。

## 2. 现有代码与可复用字段梳理

### 2.1 活动字段

来源：`backend/models.py`、`backend/database.py`、`backend/routes/activities.py`

现有活动对象可复用字段如下：

| 字段 | 用途 |
|---|---|
| `activities.id` | 反馈归属活动的主键 |
| `activities.title` | 前端展示反馈所属活动名称 |
| `activities.start_time` | 判断活动是否已结束、反馈是否来自活动后 |
| `activities.location` | 判断是否涉及集合地点、路线起终点、场地环境 |
| `activities.route` | 判断路线相关反馈，例如路线清晰度、路况问题 |
| `activities.distance_km` | 判断距离是否与成员预期不一致 |
| `activities.pace_group` | 判断配速相关反馈，例如太快、太慢、分组不清 |
| `activities.description` | 判断活动说明是否足够清楚，可用于困惑类标签参照 |
| `activities.max_participants` | 判断是否涉及人太多、组织压力、名额体验 |

### 2.2 成员字段

| `members.pace` | 辅助理解配速相关反馈 |
| `members.usual_distance_km` | 辅助理解距离强度反馈 |
| `members.training_goal` | 辅助理解训练目标与活动匹配度 |

### 2.3 报名、签到与参与分析字段

来源：`registrations`、`attendances`、`migrations/004_activity_participation_indexes_and_view.sql`

项目已有 `activity_participation_facts` 视图，可统一判断报名、签到与实际参与状态。可复用字段如下：

| 字段 | 用途 |
|---|---|

| `member_id` | 关联反馈提交成员 |

| `attendance_status` | 判断反馈成员是否实际签到 |

| `gps_checked` | 辅助判断签到可信度 |
| `registered_at` | 判断报名时机是否影响体验 |

### 2.4 反馈数据现状

当前仓库中未看到已实现的活动反馈表、反馈接口或反馈页面。任务要求设计“活动反馈情绪标签”，因此首版建议新增一个轻量反馈承载字段，但不必马上新增复杂关联表。

如果后续实现反馈功能，建议每条反馈至少包含：活动、成员、文本内容、评分、标签数组、标签置信度、人工修正状态。若先做最小版本，也可以在活动复盘文档或后台录入表单中临时保存标签结果。

## 3. 标签设计原则

1. 标签必须是中文可读名称，管理端一眼能理解。
2. 标签只描述反馈表达的情绪或问题类型，不替用户做复杂结论。
3. 同一条反馈可以命中多个标签，例如“路线不错，但集合点太难找”可同时标记“正向认可”和“信息困惑”。
4. 首版采用关键词与字段规则，不使用 AI 语义判断。
5. 每个标签都必须允许人工取消，避免误判影响运营判断。
6. 管理端默认展示高优先级标签：安全风险、组织混乱、强度不适、改进建议。

## 4. 中文情绪标签表

| 标签 key | 标签名称 | 情绪方向 | 运营含义 | 触发规则 |
|---|---|---|---|---|
| `positive_recognition` | 正向认可 | 正向 | 成员对活动整体满意，可用于复盘亮点 | 反馈文本包含“很好”“不错”“满意”“开心”“喜欢”“下次还来”“组织得好”“体验好”等词 |
| `route_satisfaction` | 路线满意 | 正向 | 路线、风景、距离安排得到认可 | 文本同时包含“路线/路况/风景/距离/补给点”之一和“好/舒服/合适/清楚/喜欢”之一 |
| `pace_discomfort` | 配速不适 | 负向 | 配速组或带跑节奏需要调整 | 文本包含“太快”“太慢”“跟不上”“拉爆”“掉队”“配速不稳”“分组不合理”等词；或活动 `pace_group` 非空且反馈提到“配速” |
| `distance_pressure` | 距离压力 | 负向 | 活动距离与成员能力不匹配 | 文本包含“太远”“距离太长”“跑不完”“强度大”“累坏”“超出预期”等词；成员 `usual_distance_km` 明显低于活动 `distance_km` 时提高优先级 |
| `info_confusion` | 信息困惑 | 中性偏负 | 活动说明、集合、路线或规则不清楚 | 文本包含“不清楚”“没看懂”“不知道”“找不到”“集合点”“时间不明确”“路线不明”“说明太少”等词 |
| `organization_issue` | 组织混乱 | 负向 | 签到、分组、集合、带队流程需要复盘 | 文本包含“混乱”“没人带”“等太久”“排队”“分组乱”“通知晚”“找不到人”“签到麻烦”等词 |
| `safety_risk` | 安全风险 | 高风险 | 需要优先处理，可能涉及伤病、夜跑、路况和车辆 | 文本包含“摔倒”“受伤”“危险”“车多”“路灯少”“迷路”“抽筋”“中暑”“补给不足”“安全隐患”等词 |
| `weather_environment` | 环境影响 | 中性偏负 | 天气、场地、路况对体验产生影响 | 文本包含“太热”“太冷”“下雨”“积水”“风大”“路滑”“空气差”“人多”“施工”等词 |
| `social_connection` | 社交融入 | 正向或中性 | 反映新成员融入、同伴氛围和带跑陪伴 | 文本包含“认识朋友”“氛围好”“有人陪”“新手友好”“融入”“大家很热情”“没人理”等词；若含“没人理/插不上话”则标为中性偏负 |
| `improvement_suggestion` | 改进建议 | 建议 | 成员提出明确可执行建议 | 文本包含“建议”“希望”“能不能”“下次可以”“最好”“增加”“减少”“提前”“优化”等词 |

首版必须至少实现前 8 个标签；推荐把 10 个标签全部作为配置常量，便于前端统一展示。

## 5. 触发规则说明

### 5.1 文本预处理

1. 去除首尾空格，把全角标点统一为普通分隔符。
2. 保留中文原文，不做翻译。
3. 文本为空或少于 2 个汉字时，不触发情绪标签，只返回空状态。
4. 对“还行”“一般”“可以但”等弱表达保持低置信度，不直接标为强正向或强负向。

### 5.2 多标签命中

一条反馈最多建议自动展示 3 个标签，排序规则如下：

1. `safety_risk` 永远最高优先级。
2. 负向体验类优先于正向认可类。
3. 明确建议类 `improvement_suggestion` 优先于普通中性描述。
4. 如果同类标签超过 3 个，只展示优先级最高的 3 个，详情中保留全部候选标签。

### 5.3 置信度建议

| 置信度 | 条件 | 前端表现 |
|---|---|---|
| 高 | 命中强关键词，且文本上下文没有否定词 | 实心标签，可直接用于统计 |
| 中 | 命中普通关键词，或与活动字段有关联 | 普通标签，允许管理员确认 |
| 低 | 只命中模糊词，例如“一般”“还行”“有点” | 虚线标签，默认不计入汇总 |

否定词包括“不”“没有”“不是”“并不”“没觉得”。例如“路线不危险”不应自动触发“安全风险”。

### 5.4 字段辅助规则

字段辅助规则只用于提高或降低优先级，不应在没有反馈文本时单独生成情绪标签。

| 场景 | 字段辅助判断 |
|---|---|
| 配速不适 | `activities.pace_group` 非空，且文本提到“配速/跟不上/太快/太慢” |
| 距离压力 | `activities.distance_km > members.usual_distance_km * 1.5`，且文本提到“累/太远/跑不完” |
| 信息困惑 | `activities.route` 或 `activities.description` 为空，且文本提到“路线/说明/集合点” |
| 组织混乱 | `max_participants >= 30`，且文本提到“排队/等/分组/签到” |
| 反馈可信度 | `participation_status = 'signed_in'` 的成员反馈优先计入活动复盘统计 |

## 6. 后端存储字段方案

### 6.1 推荐最小反馈表

如果项目后续要实现活动反馈，建议新增 `activity_feedbacks` 表。该表是独立反馈能力所需，不是单纯为了标签而新增。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | INTEGER PRIMARY KEY | 反馈主键 |
| `activity_id` | INTEGER NOT NULL | 关联 `activities.id` |
| `member_id` | INTEGER NOT NULL | 关联 `members.id` |
| `rating` | INTEGER NULL | 可选评分，范围 1 到 5 |
| `content` | TEXT NOT NULL | 中文反馈原文 |
| `sentiment_tags` | TEXT NOT NULL DEFAULT '[]' | JSON 数组，保存标签 key 列表 |
| `tag_details` | TEXT NOT NULL DEFAULT '{}' | JSON 对象，保存命中词、置信度、人工修正信息 |
| `review_status` | TEXT NOT NULL DEFAULT 'auto' | `auto`、`confirmed`、`corrected`、`ignored` |
| `created_at` | TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP | 提交时间 |
| `updated_at` | TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP | 更新时间 |

推荐约束：

- `rating` 为空或在 1～5 之间。
- `review_status` 只允许 `auto`、`confirmed`、`corrected`、`ignored`。
- `activity_id` 删除时级联删除反馈。
- `member_id` 删除时级联删除反馈。

### 6.2 不新增表的临时落地方式

如果当前迭代不做反馈提交，只做活动复盘展示，可先使用后端常量或文档规则输出：

```json
{
  "activity_id": 12,
  "feedback_summary": {
    "total_feedbacks": 0,
    "tags": []
  },
  "empty_state": "暂无活动反馈，活动结束后可邀请已签到成员填写体验。"
}
```

这种方式不保存用户反馈，只为前端预留展示结构，避免为了方案设计过早引入数据库变更。

## 7. 后端接口建议

### 7.1 创建反馈

`POST /api/v1/activities/{activity_id}/feedbacks`

请求示例：

```json
{
  "member_id": 8,
  "rating": 4,
  "content": "路线很好，但集合点有点难找，希望下次提前发定位。"
}
```

返回示例：

```json
{
  "id": 31,
  "activity_id": 12,
  "member_id": 8,
  "rating": 4,
  "content": "路线很好，但集合点有点难找，希望下次提前发定位。",
  "sentiment_tags": ["route_satisfaction", "info_confusion", "improvement_suggestion"],
  "tag_details": {
    "route_satisfaction": {"confidence": "high", "matched_words": ["路线", "很好"]},
    "info_confusion": {"confidence": "medium", "matched_words": ["集合点", "难找"]},
    "improvement_suggestion": {"confidence": "high", "matched_words": ["希望", "下次", "提前"]}
  },
  "review_status": "auto"
}
```

### 7.2 活动反馈汇总

`GET /api/v1/activities/{activity_id}/feedback-summary`

返回示例：

```json
{
  "activity_id": 12,
  "total_feedbacks": 18,
  "signed_in_feedbacks": 15,
  "average_rating": 4.3,
  "top_tags": [
    {"key": "positive_recognition", "name": "正向认可", "count": 12},
    {"key": "info_confusion", "name": "信息困惑", "count": 4},
    {"key": "improvement_suggestion", "name": "改进建议", "count": 3}
  ],
  "risk_tags": [
    {"key": "safety_risk", "name": "安全风险", "count": 1}
  ]
}
```

### 7.3 人工修正标签

`PATCH /api/v1/activities/{activity_id}/feedbacks/{feedback_id}/tags`

用途：管理员确认、删除或补充自动标签，降低误判影响。

## 8. 前端展示入口

### 8.1 活动详情页

在活动详情页添加“反馈情绪”模块，位置建议放在报名与签到统计之后、活动复盘之前。

模块内容：

1. 总反馈数。
2. 平均评分。
3. Top 3 标签胶囊。
4. 高风险标签单独红色提示。
5. “查看反馈明细”入口。

### 8.2 数据统计页面

在现有数据统计页面增加“近 10 场活动反馈趋势”卡片。

展示内容：

- 正向认可数量趋势。
- 安全风险与组织混乱次数。
- 改进建议数量。
- 反馈率：`提交反馈人数 / signed_in 人数`。

### 8.3 管理端反馈明细

反馈明细列表字段建议：

| 列 | 内容 |
|---|---|
| 成员 | 成员姓名与角色 |
| 参与状态 | 已签到、缺席、已取消、未签到 |
| 评分 | 1～5 星或“未评分” |
| 反馈内容 | 原文摘要，最多两行 |
| 情绪标签 | 标签胶囊，支持人工删除 |
| 状态 | 自动、已确认、已修正、已忽略 |
| 操作 | 确认标签、编辑标签、忽略反馈 |

## 9. 空状态方案

| 场景 | 文案 | 操作建议 |
|---|---|---|
| 活动未开始 | “活动尚未开始，结束后可收集成员反馈。” | 不展示提交入口 |
| 活动已结束但无人反馈 | “暂无活动反馈，可邀请已签到成员填写 1 分钟体验。” | 展示“复制反馈邀请文案”按钮 |
| 有反馈但无标签 | “反馈已收到，暂未识别出明确情绪标签。” | 展示原文，允许管理员手动添加标签 |
| 仅有低置信度标签 | “系统只识别到弱信号，建议人工确认后再计入统计。” | 标签显示虚线样式 |
| 反馈接口异常 | “反馈数据暂时不可用，请稍后刷新。” | 保留活动基础信息，不阻塞活动详情页 |

## 10. 误判处理方案

1. 每条自动标签都保存 `matched_words`，管理员能看到触发原因。
2. 管理员可以删除某个标签，被删除标签写入 `tag_details.ignored_tags`。
3. 管理员可以补充标签，补充标签写入 `tag_details.manual_tags`。
4. 被人工修正后的反馈 `review_status` 改为 `corrected`。
5. 统计页面默认同时显示“自动标签”和“已确认标签”口径，避免自动误判影响决策。
6. 含否定词的句子默认降置信度。例如“没有觉得危险”不计入安全风险。
7. “一般”“还行”“可以”不直接计入负向，只作为低置信度中性信号。
8. 对同一成员同一活动的多条反馈，统计时可以只计最新一条，避免重复放大情绪。

## 11. 最小落地步骤

1. 在后端新增标签配置常量，包含标签 key、中文名、优先级、关键词、颜色类型。
2. 新增一个纯函数 `detect_feedback_sentiment_tags(content, activity=None, member=None, participation=None)`，输入反馈文本和可选上下文字段，输出标签数组与命中详情。
3. 为该纯函数补充单元测试，覆盖正向认可、信息困惑、安全风险、改进建议、否定词误判、多标签命中和空文本。
4. 如果本迭代实现反馈提交，再新增 `activity_feedbacks` 表和创建反馈接口；如果不实现提交，则只在接口设计文档中预留结构。
5. 在活动详情页增加反馈情绪汇总卡片，优先展示 Top 标签、高风险标签和空状态。
6. 在管理端反馈明细中允许人工确认、删除和补充标签。
7. 数据统计页面只统计 `review_status != 'ignored'` 的反馈，安全风险标签单独高亮。
8. 上线后先观察 1～2 周误判样本，再调整关键词配置，不急于引入复杂模型。

## 12. 验收标准

1. 文档包含不少于 8 个中文情绪标签，本方案提供 10 个。
2. 每个标签都有标签 key、中文名称、情绪方向、运营含义和触发规则。
3. 文档明确复用了活动、成员、报名、签到和参与分析字段。
4. 文档给出了后端存储字段、前端展示入口、空状态和误判处理方案。
5. 最小落地步骤可由一个后端或前端 worker 拆分实现，不要求一次性改完整个系统。
